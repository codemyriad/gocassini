### Added
- The production deploy is now a committed, parameterised script
  (`ops/deploy/deploy-exapp.sh`) driven by an inventory file, instead of a
  one-off on a maintainer's laptop. It is dry-run by default, reads the live
  rollback target before touching anything, and refuses to deploy a moving tag
  (`latest`, `latest-cuda`, …) or an image whose child manifests are missing
  from the registry. CPU and GPU deployments differ by one inventory value, the
  daemon's compute device — there is no separate GPU path.
- `docs/exapp-update-constraints.md` states what the Nextcloud admin UI's
  Install and Update buttons can and cannot deliver — most importantly that
  deploy environment is applied at container creation only, so a release adding
  a *required* environment variable is a breaking change the Update button
  cannot deliver.

### Changed
- The AppAPI register logic is now one implementation
  (`ops/deploy/lib/exapp-register.sh`) shared by the sandbox, the harness
  install phase and the production deploy, so the rules that protect the
  recording archive hold everywhere: unregister before re-register, never pass
  `--rm-data`, and force `PUT /enabled` so the navigation entries come back.
- The ExApp install guide now documents the `/exapps/*` reverse-proxy route to
  HaRP. It is required for every HaRP daemon and is what actually blocks an
  install when missing — the symptom is an app that reports `[enabled]` with no
  navigation icon, which points nowhere near the reverse proxy. It must use
  Caddy's `handle`, not `handle_path`, so the prefix survives.
