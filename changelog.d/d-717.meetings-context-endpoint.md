### Added
- The Cassini app can ask for a set of meetings as one document: `GET published/meetings-context?ids=…,…`, optionally `&format=json` and `&timestamps=true`. It answers with exactly what `cassini meetings context` prints for the same meetings — the operator resolves what you may read the same way it resolves the meeting list, fetches each recording from Nextcloud Files as you, and runs the CLI over them, so there is one implementation of the document rather than one per reader. An id you may not read is answered `404`, identically to one that does not exist; a request that cannot be answered is `502`, never an empty document. At most 20 meetings per request, because each one costs a whole recording download.
- `cassini meetings context --local ./Meeting.opus [...]` reads portable `.opus` files off disk instead of fetching meeting ids from Nextcloud, and needs none of the connection settings. Each meeting's id is its file's basename without the `.opus`, which is how a published archive names one. `--catalog ./catalog.json` supplies the room id and room name, which live in the catalog rather than in the file — with it, a run over an archive's files produces the same bytes as a run over the same meeting ids; without it a meeting renders with the room id its file was tagged with and no room name.

Ids travel as one comma-separated `ids`, not as a repeated `id`: AppAPI's proxy collapses repeated query parameters to the last value, which would have answered a three-meeting request with a one-meeting document and a `200`. A caller reaching the operator directly may still repeat `id`.
