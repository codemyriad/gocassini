### Added
- Source-side audio capture, first stage: while Talk's official recording is active, a participant's browser can now record its own microphone before Opus encoding and before the network, then upload as soon as Talk confirms recording stopped. A small same-version `cassini_capture` companion app loads the capture payload on authenticated Talk calls through Nextcloud's public additional-scripts event; it does not intercept or rewrite Talk's bundle. Reloading during a recording resumes from Talk's room state, retries the durable pre-reload prefix, and limits an abrupt-navigation gap to a two-second checkpoint; leaving remains a stop/upload fallback. Cassini's recorder subscribes through the SFU, so until now the transcript could only ever be as good as each participant's uplink — words lost to packet loss were simply gone. The build can transcribe a speaker from that audio instead of from what survived their uplink, and a capture is only used when it comes from the same room and an overlapping call. Placement takes its rate from the participant's own encoded-frame timestamps — immune to packet loss, because those describe frames the client encoded rather than packets that arrived — and its offset from a wall-clock anchor the recorder now records per track. Offset accuracy is therefore bounded by how well the participant's clock agrees with the server's; a placement that falls outside the recording is refused, and every other failure leaves that speaker on the recorded track. Capture follows Talk's own official recording — consent is Talk's, through its recording indicator and its recording-consent setting, and Cassini adds no participant surface of its own. It records the track Talk is sending (so Talk's own mute is honoured at the source and cannot be bypassed), and every upload is filed under the AppAPI-authenticated caller and refused for a room they were not in. The published audio stays the recorded mix — that is the meeting as everyone in the room heard it — and manifest.provenance.sourceAudio records which speakers were transcribed from their own capture and how well it fitted. Ingestion is also contained so it can never cost a meeting: the decode of participant-supplied media is bounded by a deadline and cancelled with the build, a WAV that cannot be written says so instead of being handed on as if it were whole, and a capture set aside while a re-upload is promoted is no longer discovered as a second capture for the same speaker. A client whose upload is refused for good now discards it rather than re-uploading a meeting-sized body on every Talk page load. A capture cut into more than one segment — which happens whenever a participant changes microphone during a recorded call — was refused by the server and never stored, because Nextcloud's AppAPI proxy rebuilds the upload through PHP and PHP keeps only the last file sent under a repeated field name; segments are now identified by their file name, which survives that hop. Disabling the app now really does turn collection off: the switch is written back to Nextcloud before the app answers the lifecycle call, instead of in a goroutine racing the container's own shutdown, which previously left the stored value saying enabled and the companion still injecting the capture payload into Talk call pages. A capture is now refused when it does not cover the call it came from. Substitution is whole-track, so a capture that succeeds while holding only part of a call turned the rest into silence with the recorded track suppressed underneath it, deleting speech the recorder had heard perfectly well; the manifest records how much of its call each capture covered, either way. Both switches are ON by default on this branch, which exists to run the feature end to end: CASSINI_SOURCE_CAPTURE collects, CASSINI_SOURCE_AUDIO_INGEST lets what was collected reach a transcript, and each is an explicit opt-out — set it to 0 (or false) to turn that half off, while a value that is neither also lands off and is logged. Ingestion left on costs nothing where nothing was collected: the build finds no upload for the room and transcribes the recorded tracks unchanged, leaving the same bundle it would have produced with ingestion off. The demo sandbox deploys the feature end to end with no flags: `sandbox/wire-cassini.sh --image ...` passes both switches at registration and installs the `cassini_capture` companion from the payload the deployed image serves; `CASSINI_SOURCE_CAPTURE=0` in the environment stops collection again, companion included; turning the feature off completely means `CASSINI_SOURCE_AUDIO_INGEST=0` as well, because captures already stored survive until the retention sweep reaches them and a deferred build or a rerun would still transcribe from them. The Deploy Sandbox workflow drops its two inputs for the same reason. Installing the companion still needs an image built from the deploying checkout, so a store deploy leaves Talk pages without the payload and says so rather than failing.
- The recorder now writes `first_timeline_ns` as a position on the meeting timeline. It wrote the raw receive clock, so on every real recording the transcriber computed a negative search window and never found an upload; the splice only ever ran in unit tests. Recordings made before this carry the stream placement tags, and the transcriber recovers the anchor from those.
- A participant's capture that arrives after the transcript has been made no longer sits on disk unused. The build is queued the moment Talk reports the recording stopped and the browser starts uploading on that same signal, so on any link slower than the build itself the audio was too late — and a slow link is the whole reason the feature exists, which made the audio most worth having the audio most likely to be missed; on the demo the build started one second before the upload landed, and the meeting had to be rerun by hand. An upload is now matched to its recording by Talk room AND overlapping call window (never the room alone, and never a guess between two recordings that both match — that is refused, and logged), and the meeting is transcribed again as an ordinary rerun attempt with its own build, seal and publish, so nothing overwrites the published meeting in place and a rebuild that dies half way leaves the previous one exactly as it was. The intent lives in the job database, so it survives a restart and an interrupted rebuild is simply still owed on the next pass; a wave of uploads from one call coalesces into a single rebuild; and a rebuild is refused when it would read the same bytes the last build already read, when the capture has since been swept, when the meeting is older than the capture retention window, or after three rebuilds of one meeting. `/operator/status` and the job JSON report a pending rebuild.
