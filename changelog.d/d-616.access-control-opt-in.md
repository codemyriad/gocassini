### Added
- **Access control is now a choice rather than a requirement.** Cassini used to have exactly one way to store recordings — a Nextcloud Team folder with per-recording permissions — which needs two Nextcloud apps an external app cannot install for itself, so an instance without them recorded meetings happily and then could not publish any of them. There are now two storage modes, switched in a new admin-only **Setup** tab: **default**, where recordings live in the `cassini` service account's own `CassiniNoACL/Recordings` and everyone who can open Cassini can read all of them, needing no extra apps at all; and **access controlled**, which is exactly today's model in its `Cassini` Team folder. Each mode has its own folder, so neither can shadow the other's path.
- **Cassini can set itself up.** The Setup tab offers to make the changes an administrator used to make by hand: the `cassini` service account and its group, the Team folder, its group mappings, advanced permissions, and the permission-manager delegation. It lists every change before it makes any of them, and performs them as you — Nextcloud asks you to confirm your password with its own dialog, and Cassini never sees, stores or sends it. The `occ` recipe is still there for an administrator who would rather run it, and is generated from the same plan the Setup tab executes, so the two cannot describe different setups.
- **Every missing prerequisite is named, together with the `occ` command that fixes it.** The Setup tab and `GET /operator/status` list them all — the service account, each Nextcloud app, the Team folder, its group mappings, its ACL setting and its ACL manager — and the notice on the meeting list now leads with the offer to fix them rather than with a recipe to copy into a terminal.
- **A deployment can declare which storage mode a fresh install starts in**, with the `CASSINI_STORAGE_MODE` deploy option (`default` or `access_controlled`). It seeds the initial value only: the Setup tab is where the mode changes afterwards, and changing the variable never moves an archive that already exists.
- **Switching modes says what it would do before it does it, and can be re-run.** The confirmation reports how many recordings would move and between which folders, whether the destination already holds any, and whether an earlier switch left a copy behind. Working that out is read-only, and nothing happens until you confirm. The switch itself copies the archive, checks every recording arrived, records the new mode, and only then empties the old folder — so whichever mode is in force, that folder holds a complete archive, and a switch interrupted by a restart, a timeout or a closed browser tab strands nothing and can simply be asked for again. The Setup tab names the folder that still holds a leftover copy and offers one button to clear it, and says when recordings are sitting in the mode that is *not* in force.

### Changed
- **Cassini never infers its storage mode from the instance.** It uses the mode it recorded, or the `CASSINI_STORAGE_MODE` deploy option, or falls back to the default model — it never reasons "this Nextcloud has a Team folder, so it must want access control". Inferring made who can read the archive depend on what Nextcloud happened to look like at one instant, and on an instance still being assembled that instant is the wrong one. A recorded mode is authoritative for the life of the install; nothing re-opens it. Storage that does not match the mode is reported as a mismatch that refuses to publish and names both ways out, and a Team-folder list Cassini cannot read counts as an unanswered question rather than as "there is no Cassini Team folder" — the folder list arrives with every folder on the instance in one response, so a single unrelated folder in an unexpected shape used to make the whole answer undecodable and indistinguishable from an empty one.
- **An existing access-controlled installation should declare its mode when it updates.** Nothing has recorded one, so it falls back to the default model. An instance whose Team folder still holds published recordings notices that, refuses to publish, and says so — turn access control on in the Setup tab, or set `CASSINI_STORAGE_MODE=access_controlled` and re-enable the app. Nothing is moved and no archive is widened while it waits; the refusal is deliberate, chosen over guessing. An access-controlled instance with no published recordings yet has nothing to notice, so declare the mode there before recording anything.
- **Cassini no longer creates Nextcloud accounts, groups or Team folders on its own.** On every enable it checks what is there and reports what is not; it makes those changes only when you ask for them from the Setup tab. A half-built setup can no longer end up looking healthy.
- **Talk refuses to start a recording when the storage it would be published to is missing a named prerequisite**, instead of capturing the whole call and failing afterwards. The moderator sees Talk's own "The recording failed" message; the reason, and the command that fixes it, are in Cassini's Setup tab.
- **Installing the two Nextcloud apps is the one step Cassini still cannot take for you, and it now says so** instead of implying otherwise. Nextcloud requires an administrator's password on that particular request, which Cassini declines to handle; it attempts the install through its own backend — which works on Nextcloud 32.x, 33.0.0–33.0.5, 34.0.0, and on any release where `allowed_no_password_confirmation_ranges` is set — and otherwise links you to Nextcloud's own Apps page, where that flow lives. When the App Store refuses, the message says plainly that Nextcloud reports the same error whether the app is unknown, incompatible or the store is unreachable, and that retrying inside five minutes will say the same thing.
- **`backfill-nc-files` refuses to run on an installation using the default storage model**, instead of writing access rules into a folder where they mean nothing. Everything it writes is protected by Team-folder permissions, and the default model keeps recordings in the `cassini` account's own folder where every signed-in account can already read them — so the migration would be at best a no-op with side effects, and at worst would re-derive an audience for recordings an administrator had deliberately left open. The refusal names the mode, writes nothing, and points at the Setup tab, which is what actually moves an archive between the two models.
- **The recordings-permissions, install and privacy documents now describe both modes.** The upgrade section in particular had the Team-folder path collision backwards — a Team folder takes the `Cassini` path and Nextcloud renames the colliding home directory, rather than the mount being remapped — so its instruction to move the old folder out of the way first was unnecessary.

### Fixed
- **Restarting the Cassini container no longer stops it publishing until an administrator disables and re-enables the app.** Cassini checked how Nextcloud is set up on the app's enabled edge, and that check was the only thing that could mark the storage usable — so a plain restart left it reporting an unknown state and refusing to publish, with nothing obviously wrong. It now re-checks at startup as well, for installations that have already recorded which storage model they use. A first install is unaffected: Nextcloud rejects the calls until registration finishes, so that case still waits for the enabled edge, which fires moments later.
