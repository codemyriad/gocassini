# Changelog

All notable user-facing changes to Cassini will be documented in this file.

This project follows semantic versioning for Nextcloud App Store releases.
The version in `appinfo/info.xml`, the ExApp Docker image tag, and the release
archive version must match.

## [Unreleased]

Unreleased changes are collected as fragments in `changelog.d/`. Versioned

`scripts/prepare-release.sh`) folds those fragments into this file under the new
version and removes the consumed fragments. Edit released sections only to fix

## [0.2.0-beta.7] - 2026-09-20

### Added
- **Access control is now a choice rather than a requirement.** Cassini used to have exactly one way to store recordings — a Nextcloud Team folder with per-recording permissions — which needs two Nextcloud apps an external app cannot install for itself, so an instance without them recorded meetings happily and then could not publish any of them. Recordings can now be visible to **anyone with a Nextcloud account**, in the `cassini` service account's own `CassiniNoACL/Recordings`, needing no extra apps at all; or to **meeting participants** only, which is exactly today's model in its `Cassini` Team folder. Each has its own folder, so neither can shadow the other's path.
- **Cassini can set itself up.** It offers to make the changes an administrator used to make by hand: the `cassini` service account and its group, the Team folder, its group mappings, advanced permissions, and the permission-manager delegation. It lists every change before it makes any of them, and performs them as you — Nextcloud asks you to confirm your password with its own dialog, and Cassini never sees, stores or sends it. The `occ` recipe is still there for an administrator who would rather run it, and is generated from the same plan Cassini executes, so the two cannot describe different setups.
- **Every missing prerequisite is named, together with the `occ` command that fixes it.** Cassini and `GET /operator/status` list them all — the service account, each Nextcloud app, the Team folder, its group mappings, its ACL setting and its ACL manager.
- **A development or CI deployment can still declare the mode**, with the `CASSINI_STORAGE_MODE` deploy option (`default` or `access_controlled`). It is not for production installs, and it is believed only where it fits: a declared mode whose prerequisites are missing, or that meets recordings in both folders, or the same recording in both, is refused at enable time and not recorded. It seeds the initial value only, and changing the variable never moves an archive that already exists.
- **Switching says what it would do before it does it, and can be re-run.** The confirmation reports how many recordings would move and between which folders, whether the destination already holds any, and whether an earlier switch left a copy behind. Working that out is read-only, and nothing happens until you confirm. The switch itself copies the archive, checks every recording arrived, records the new audience, and only then empties the old folder — so whichever audience is in force, that folder holds a complete archive, and a switch interrupted by a restart, a timeout or a closed browser tab strands nothing and can simply be asked for again. Cassini names the folder that still holds a leftover copy, offers one action to clear it, and says when recordings are sitting in the audience that is *not* in force.
- `cassini meetings summarize <meeting.opus> ...` adds a meeting summary to already-published portable files without re-running transcription: the transcript sealed inside each file feeds one LLM call — configured by the same `LLM_BASE_URL` / `OPENROUTER_API_KEY` / `SUMMARY_*` variables as `cassini build` — and the file is rewritten in place with its audio bytes untouched.
- Files that already carry a summary are skipped; `--force` regenerates and replaces one, and `--out` writes a single file's result to a new path instead of in place. A backfilled summary is marked `provenance.meetingSummary.source = "backfill"` in the manifest.
- You can find words inside the meeting you are reading. A search box above the transcript narrows it to the turns that match, shows how many of them there are, and clearing it brings the whole transcript back. It searches what was actually said, so it still finds a turn whose wording was tidied for display.
- Administrators can tell Cassini the spellings transcription produces for names it gets wrong, in the app's settings beside the existing vocabulary: one name per line, its spellings separated by commas. A search for the name then also finds the recordings where it was written down differently, and each result says whether it matched what you typed or a known mis-hearing. Cassini ships a starting list; anything configured here is added to it, and replaces it for a name that appears in both. It changes no recording — the vocabulary setting is the one that biases new transcriptions.
- You can now search across your meetings. Cassini indexes each transcript as it is published and answers `published/search` with the moments that match — the meeting, the speaker, and where in the recording they said it. You only ever see meetings you can already open.
- Search knows the names transcription gets wrong. Looking for "cassini" also finds the recordings where it was written down as "casino", and each result says whether it matched your words or a known mis-hearing of them.
- Every answer says how much it covered: how many of the meetings you can read were actually searched. A meeting Cassini could not index is reported as outside coverage rather than passing for one with no matches, and an unreachable archive is an error rather than an empty result.
- Cassini's search index lives in its own `search.sqlite3` file beside the job database and holds nothing that cannot be rebuilt from the published recordings. Deleting it is safe: it costs a rebuild and never touches recordings or job history.
- `cassini-operator backfill-search` indexes meetings published before the index existed. It is safe to re-run and safe to interrupt, and it indexes a meeting only when the stored transcript matches the recording that was delivered.
- Searches are rate limited per account. Each one asks Nextcloud what that person may read, so a client looping on search would put that load on Nextcloud rather than on Cassini; a burst is fine and a loop is asked to slow down, with a reply that says when to retry. The limit is per account, so one runaway client cannot lock anyone else out.
- Pick several meetings in the Cassini app — across rooms, and the picks survive changing the room or the search — and Prepare hands you all of them as one document to copy or download. It is the same document `cassini meetings context` prints for the same meetings in the same order, byte for byte, because the app asks the same producer for it rather than assembling its own.
- Before it hands anything over, Prepare says what the bundle will not contain: how many of the picked meetings have no summary, how many were published before the index recorded whether they have one — a different statement, and never counted as the first — how many predate the single-file format, and whether the word count it shows is a total or a floor. All of it is read from the published meeting index, so nothing is downloaded to answer it.
- A meeting that leaves the archive while it is picked is removed from the selection and said so, rather than quietly shrinking the document you were about to hand over.
- A portable export offers no Prepare at all. There is no operator behind an exported site to assemble a bundle, and producing a lookalike in the browser would be a second implementation of a published format.
- `GET /jobs` returns `room_name`, the conversation's display name as it was when the job ran. The operator now stores the room as real columns on the job rather than only inside its Talk binding, and recovers them for every recording it has already made, so a room-scoped question is an ordinary query rather than a JSON parse. The conversation's token gets a column but is deliberately left out of the response, for the same reason the Talk binding has always been withheld from it.
- The meeting list is organised by room. A rooms nav down the left lists every room the archive knows about with its meeting count, alongside "All meetings" and a "No room" group that keeps recordings without a room — an imported file, a simulated run, an old recording — visible rather than hidden.
- Meetings are grouped under month headings, and each row now shows its room, its date, its speaker count and how long it ran.
- `cassini insight run` asks one question of several meetings and writes the answer. It reads the context bundles `cassini meetings context --json --out` produces — one `--context` per bundle, in the order you name them — runs the summarise workflow over all of them at once, and writes the result to `--out` or to standard output. `--model` overrides the model for that run alone, and `--timestamps` shows the model where in each meeting something was said so it can cite it.
- The document it writes carries its own provenance as frontmatter: which meetings it was produced from, with their rooms; the workflow's id, version and the content hash of the exact prompt bytes that produced it; the endpoint and model that answered; and when. A summary has always been able to say only that some model wrote it at some point, which is not enough to tell two documents from different prompt versions apart. `--record` writes the same record as JSON beside the document, so a grading harness reads one pair rather than parsing prose.
- `cassini insight run` exits with a different code per outcome — no endpoint configured, the endpoint refused, the model failed or timed out, a bad request — instead of warning and carrying on. Skipping quietly is reasonable for a summary nobody asked for and never for a document somebody did. The codes are listed in `cassini insight run --help`. A failed run still writes its `--record` file, saying what was attempted and why it did not happen.
- Transcripts now carry cross-track speaker attribution evidence. Every word records how far the loudest other participant's microphone sat above its own noise floor compared with the speaker's own, so crosstalk the decoder transcribed as speech becomes visible instead of shipping unmarked. Where a meeting's own level distribution shows an unambiguous crosstalk population, affected words are flagged `lowConfidenceSpeaker`; the canonical transcript keeps every word, and the evidence travels with them as `attributionGapDb`.
- Generated summaries now exclude words flagged as probable crosstalk. A reader can see and overrule a marked word in the transcript; a summary has no such reader, and a fabricated interjection there becomes a decision somebody supposedly made.
- Speech recognition now runs behind a backend interface, so a second engine can be added by registering a factory rather than by changing the pipeline. Select one with `CASSINI_STT_BACKEND`; the bundled sherpa-onnx decoder remains the default, and an unknown selection fails loudly rather than silently transcribing with a different engine.
- The viewer now surfaces the crosstalk evidence the transcript carries. A turn built entirely from words the acoustic evidence attributes to somebody else is badged "probably crosstalk", and in the exact-word view individual flagged words are de-emphasised with a dashed underline and a tooltip saying how many dB louder the other microphone was. The words are still shown and still seekable — the reader can listen and decide.
- Added a standalone waveform challenge miner that finds tricky meeting sections, including overlapping speakers, without rerunning speech recognition.
- A published meeting now records how its word ends were decided, as `provenance.wordTimings.endsBoundedByAudio` in the portable-meeting manifest. When the key is absent, a consumer may repair an over-long word by clipping it towards the meeting median; when present, the end was measured against audio and must be preserved.
- A Settings surface in the app, beside Browse and Operator (admins only). It hosts transcription quality — moved off the operator page — and the new LLM settings: endpoints, whether summaries run and on which endpoint and model (with a fetched model list). Each endpoint carries its own request bounds — timeout and response-token limit — with empty fields meaning the defaults (900s / 4096).
- The app keeps its own LLM settings (`llm-settings.json` beside the job database; `GET`/`PUT /settings/llm`): named endpoints, and the summary policy. Switching between a hosted provider and a self-hosted model server is one settings change, with no ExApp redeploy. `GET /settings/llm/providers/{id}/models` lists what an endpoint serves. API keys are stored server-side and never returned.
- Generate an insight from inside the app. Pick meetings in the browse list, open **Prepare context**, and the panel now offers a Generate card under Copy and Download: choose one of the templates this deployment ships and press Generate. The transcripts go to the AI endpoint you picked and the answer is written into your own Nextcloud files.
- Insight runs report themselves honestly rather than as a spinner. A run appears in the card the moment you press Generate and carries `queued`, then `running`, then a result or a failure — a local model over five meetings takes minutes, and the card says so instead of implying seconds. A failed run names the cause in words you can act on ("No AI endpoint is configured", "The endpoint rejected the request"), carries **Retry**, and — for an administrator — links straight to the AI providers panel that fixes it. Retry replays the request as you made it, to the endpoint you picked; it falls back to the deployment's configured endpoint only if you picked none, or the one you picked has since been removed — which is what makes adding an endpoint a fix rather than a suggestion.
- **Ask your own question.** One shipped template, "Ask your own question", takes a question you type and answers it from the meetings you picked: the answer in at most three sentences, the evidence with who said what, and what these meetings do not answer. The question box appears for that template and for no other — every other template asks its own question, and a question sent to one of those would be dropped without being asked, so it is refused rather than silently discarded. `cassini insight run` gained the matching `--question` flag.
- Insights are reachable from the browser: the manifest declares three new USER routes — `insights` (create a run, list your own), `insights/<id>` (read one with its document) and `insights/<id>/retry`. They are the first routes in Cassini a logged-in non-administrator may POST to, and they are USER rather than ADMIN because a run acts only within what that person could already do by hand: it reads the meetings they picked, as them, and writes the answer into their own Nextcloud Files. **On upgrade** an existing install picks the new routes up from the release itself — no re-registration needed, because every release bumps `<version>` (see below).
- An insight you ask for in the app is answered by the deployment on your behalf and delivered into your own Nextcloud Files, under a **Cassini Insights** folder in your home. You own the file outright, so Nextcloud's own sharing works on it and nothing new decides who may read it. It is deliberately not filed under `Cassini/` — that name is the shared recordings Team folder, which is read-only for everybody but Cassini's service account — and an insight is never written next to the recordings.
- A document is never overwritten. Each file is named for the day, the template and the run it came from, and if something is already at that name the run writes the next free one and records which it used.
- Every meeting an insight covers is fetched **as you**, over WebDAV, at the moment the run happens — so Nextcloud's own per-file permissions decide what is in the bundle, and a run can only ever be assembled out of meetings you could already open yourself. A retry re-checks that: a meeting you can no longer read stops the run rather than quietly dropping out of the answer.
- A failed run says which of the five things went wrong in words that name the fix — no endpoint configured, the endpoint refused the request, the model did not answer, the answer could not be written, or the request itself — rather than reporting one general failure.
- Cassini now answers `published/meetings-list` with the meetings the calling account may read, narrowed by an optional date range or room. The viewer and the `cassini meetings` CLI previously fetched the whole catalogue and filtered it themselves; the same list is now available already filtered, in the catalogue format both already read.
- A date-filtered list reports how many meetings it dropped because their published date could not be read, so a short list is visibly partial rather than quietly incomplete.
- Unlike the catalogue it is built from, this list never answers an unreachable Nextcloud with an empty result: a substrate failure is reported as an error, and an empty list means only that the account may read no matching meeting.
- Cassini Admin's Transcription quality panel reports the device and model the
  next build will actually use, so a CPU run is stated up front rather than
  inferred from a failed build. The device override adds a **CPU** choice
  alongside Auto and CUDA.
- `cassini meetings context` takes several meeting ids and prints one document holding all of them, so a question can be asked of a set of meetings rather than one at a time. The meetings appear in the order you named them, separated by a `---` rule, and the `--json` form carries them as a `meetings` array whose every entry is exactly the single-meeting document the command has always produced. An id you cannot read — or one that does not exist, which is answered the same way on purpose — fails the whole run: a bundle that quietly dropped a meeting would answer a question asked of all of them using only some of them, and look right doing it.
- `cassini meetings context --timestamps` cites each passage's start time, as `MM:SS` or `H:MM:SS` past an hour, beside the speaker. Off by default. The timings were already in the `--json` output and had no way of reaching the text an agent actually reads, so nothing asked to say *where* something was said could point at it.
- The context bundle's format has a published schema, `spec/cassini-meetings-context-v1.schema.json`, and its output is pinned by fixtures. `cassini.meetings.context.v1` was a version string with nothing written down behind it; now a change to what the command emits shows up as a diff in a checked-in file.
- The published meeting index (`catalog.json`, and so `cassini meetings list --json`) now records whether each meeting carries a summary and how many words its transcript holds. Both come out of the file the publish step already reads, so anything listing meetings can say which of them have a summary, and size a selection of them, without downloading a single recording. Meetings published before this update carry neither field, which reads as "not known" — never as "no summary" or "no words"; republishing one fills them in.
- The Cassini app can ask for a set of meetings as one document: `GET published/meetings-context?ids=…,…`, optionally `&format=json` and `&timestamps=true`. It answers with exactly what `cassini meetings context` prints for the same meetings — the operator resolves what you may read the same way it resolves the meeting list, fetches each recording from Nextcloud Files as you, and runs the CLI over them, so there is one implementation of the document rather than one per reader. An id you may not read is answered `404`, identically to one that does not exist; a request that cannot be answered is `502`, never an empty document. At most 20 meetings per request, because each one costs a whole recording download.
- `cassini meetings context --local ./Meeting.opus [...]` reads portable `.opus` files off disk instead of fetching meeting ids from Nextcloud, and needs none of the connection settings. Each meeting's id is its file's basename without the `.opus`, which is how a published archive names one. `--catalog ./catalog.json` supplies the room id and room name, which live in the catalog rather than in the file — with it, a run over an archive's files produces the same bytes as a run over the same meeting ids; without it a meeting renders with the room id its file was tagged with and no room name.
Ids travel as one comma-separated `ids`, not as a repeated `id`: AppAPI's proxy collapses repeated query parameters to the last value, which would have answered a three-meeting request with a one-meeting document and a `200`. A caller reaching the operator directly may still repeat `id`.
- Insight templates is a real panel in the Operator: it lists every template this build ships, and each row opens onto the exact instruction that template sends to the model — the prompt itself, not a description of it — beside the id, version and content hash an insight document records. So a document you found a month later can be traced to the prompt that produced it, rather than to a name that may since have meant something else.
- A second template, "Commitments and owners": one section per person who spoke, with what they took on and when they said so, then what was assigned to somebody who never answered, then what nobody claimed. `cassini insight run --workflow todos` runs it, and every other workflow the panel lists can be named the same way.
- `cassini insight workflows` prints the same list on the command line, and `--json` adds each workflow's instruction verbatim. It is how you check what a given image will actually send, without reading its source. The Operator's templates panel is this command's output.
- LLM settings carry a second step, **Insights**, beside the meeting summary, so an insight can run on a different provider and model from the one that writes each meeting's summary — a small local model for every published meeting, a larger one for a question you ask by hand. An insight step with no endpoint of its own runs on the summary endpoint, so an existing install gains insights without configuring anything, and the settings panel says which of the two is answering. Each step also names the workflow it runs.
- Per-step request bounds (`SUMMARY_TIMEOUT_SEC` / `INSIGHT_TIMEOUT_SEC` and the matching `_MAX_TOKENS`), because two steps on two endpoints cannot share one timeout: a CPU-bound local model needs a far longer leash than a hosted API.
- Each step's workflow field is checked against the templates the image actually ships, and names them when the id is not one of them. The operator cannot know the registry — it lives in the recorder — so a typo used to save cleanly and only fail at the run.
- An insight now keeps a record of itself from the moment it is asked for, moving through queued, running and then succeeded or failed. A run that takes minutes against a local model shows what it is doing rather than nothing, and a failed one says why it failed instead of stopping silently.
- Retrying a failed insight is another attempt on the same insight, not a second one: it keeps its id, workflow, meetings, question and the endpoint you picked, and replays that request. It falls back to the deployment's configured endpoint only if you picked none, or the one you picked has since been removed — so fixing a missing key on your endpoint, or registering one where there was none, is enough to make the retry work. A retry pressed twice at once starts one attempt and refuses the other. A run the operator was restarted out from under is failed with a message asking you to retry it, instead of staying stuck on "running".
- An insight now appears in the browse list beside the meetings it was drawn from, and under every room those meetings came from: a question asked of three rooms is found in all three, not filed under one of them. A Meetings/Insights switch above the list narrows to one kind or the other, and the last kind showing cannot be switched off. Insights that are queued or still running are listed too, saying so — an answer that takes minutes is visible while it is being written rather than appearing from nowhere afterwards — and a listing that fails says it failed instead of reading as "there are none".
- Opening an insight shows the question it was asked, the meetings it read — each of which opens as itself, with the way back to the insight — the answer, and who ran it with which workflow and version. Every source meeting lists the insights that read it, so the link works in both directions. A meeting or an insight you may not read is simply absent from both, with nothing anywhere saying that it existed. The standalone viewer export, which has no operator behind it to have run anything, shows none of this and offers no filter for it.
- `GET operator/setup`, which any logged-in Nextcloud user may read, now also reports what this deployment's AI configuration allows: `features.summaries` (a recording will be summarised) and `features.insights` (a question asked of a set of meetings will reach an endpoint). One bit each — never the endpoint, the model or the key, which stay administrator-only. It makes the promise in `docs/privacy.md` — that nothing leaves your infrastructure unless an endpoint is configured — checkable by the people whose meetings are being recorded.
- The Cassini app now explains an unconfigured deployment instead of staying quiet about it: picking meetings on an instance with no AI endpoint says so in the Prepare panel, and an administrator gets a link straight to the AI providers panel that keeps the meeting they had open. Anyone who is not an administrator is told the fact and that only an administrator can change it, rather than being shown a control that would be refused. The standalone viewer export, which has no operator to ask, says nothing at all.
- **Pick the AI endpoint and model when you create an insight.** Prepare now offers a Provider and a Model beside the template, defaulting to the first configured endpoint and its own default model. It is offered to **everyone**, not only administrators: which of the configured endpoints sees your transcripts is the asker's decision, so `GET operator/ai/providers` is a USER route carrying ids and display names — the base URL, the key and the request bounds stay administrator-only. A retry re-runs what you asked for, falling back to the deployment's endpoint only if the one you chose has since been removed. **This adds a route, so the release that ships it must bump `<version>` in `appinfo/info.xml`** — AppAPI only rewrites an app's route table on a version change.
- **"Ask your own question"**, the freeform insight template. Pick it in Prepare, type a question, and the answer comes back in three parts: the answer itself in at most three sentences, the evidence with who said what and when, and — never omitted — what these meetings do not answer. The machinery for a caller-supplied question already existed (`{{QUESTION}}`, `Workflow.TakesQuestion`); what was missing was a prompt carrying the placeholder. A template that takes a question is offered wherever one can be typed and withheld where one cannot: it is not offered as the publish pipeline's summary step, which runs unattended with nobody to ask.
- The **Participant and project vocabulary** setting now guides the transcriber itself. Terms are applied as sherpa-onnx contextual biasing, so the recogniser can prefer "Librocco" or "Aire Spaces" where it used to invent a spelling. The vocabulary is a decoder prior rather than a text rewrite; its score therefore stays conservative so it does not overpower weak acoustic evidence.
- `provenance.speechToText.hints` in the build manifest records how many terms were used, the boost, and the decoding method. When a vocabulary is configured but cannot be applied, it records that and why, so a build that ignored the setting never looks like one that honoured it.
- `CASSINI_STT_HINTS_DISABLED` turns biasing off and restores greedy search, so an operator can get back to the transcription they had before; `CASSINI_STT_HINTS_SCORE` overrides the boost. Both are passed through the deployment compose file.
- The meeting list's search box now searches what was said in your meetings, not just their names and dates. A matching meeting shows the moments that matched, and clicking one opens the meeting at that point with the transcript already filtered to those lines.
- When search cannot answer — too many searches, an index still building, or an unreachable archive — the list says so instead of showing an empty result that would read as "nothing matched".
- Cross-meeting search results now carry a short quote of what matched, so a result says why it matched rather than only where.
- `cassini annotate` reads and writes the tags and marks a recording carries inside its own `.opus` file. `show` prints them. `apply` takes a batch of edits — tag the whole meeting or a stretch of it, remove a mark, remove a tag, undo everything one run added, rename a tag — and rewrites the file once, without touching the audio, the transcripts or the summary. Sending the same batch twice changes nothing the second time, and a batch that changes nothing does not rewrite the file.
- `cassini annotate carry` moves the marks from a delivered recording onto a newly sealed one, so re-running a meeting does not lose them. When the new recording's audio differs, the marks are kept and flagged as made against different audio rather than redrawn on it.
- A meeting's tags and marks can be read and changed at `annotations/meetings/<id>`, by people in the app, the CLI and agents alike. Anyone who can read a meeting can mark it, and every mark is attributed to the Nextcloud account that made it, never to a name the request supplies. The marks are written into the recording itself, so they travel with it when it is downloaded or shared.
- Two people marking the same meeting at once no longer overwrite each other: a write that finds the recording changed underneath it re-reads the newer copy and applies its marks to that. A meeting you cannot read answers exactly as one that does not exist.
- `GET annotations/tags` lists the tags on the meetings you can open, each with how many meetings and marks carry it, and says how many of your meetings it could read marks for. A tag that is only on meetings you cannot open never appears and never changes a count.
- `published/search` and `published/meetings-list` take `tag=` (a label in any case, or a tag id) and answer only from meetings carrying a mark of that tag. Each search result also lists the tags whose marked stretches it falls inside.
- Cassini keeps its tag index in its own `annotations.sqlite3` beside the job database. It holds nothing that cannot be rebuilt from the marks inside the recordings, and `cassini-operator backfill-annotations` rebuilds it: recordings that have not changed are skipped without a download, and a fresh index keeps the tag namespace the archive already uses.
- A recording can carry tags. A tag such as `hiring` can go on the whole meeting or on a stretch of it, and the marks live inside the recording's `.opus` file, so a meeting keeps its tags when it is downloaded or shared. The portable format and its schema describe them, and a reader that does not understand them still opens the recording normally.
- `cassini meetings tags` lists the tags on the meetings you can read. `cassini meetings annotations <id>` shows one meeting's marks, and `cassini meetings annotate <id> --ops <file>` adds or removes them in one batch. Every mark records the Nextcloud account that made it, and whether a person or an agent made it, so an agent's whole run can be undone in one step.
- `cassini meetings search` and `cassini meetings list` take `--tag` to look only at meetings with that tag. Against a Cassini app that does not offer tags, they fail instead of silently returning every meeting.
- `cassini inspect` reports a recording's tags: how many there are, and whether they were made against this recording's audio.
- You can tag meetings from the app. Each row in the meeting list shows its tags; tag one meeting from its row, or select several and tag them together. A filter beside the rooms narrows the list to one tag or several.
- Inside a meeting, you can tag a section of the transcript: select its words (or, on a wide screen, drag down the rail beside it), choose Tag selection, and set exactly where it begins and ends with the handles in the text or the arrow keys. Tagged sections are underlined in their tag's colour and, on a wide screen, bracketed beside the text with the tag's name; arrows step from one to the next. The last tag you used is offered again beside Tag selection, so tagging several sections alike is one click each. On a phone, a section's tag sits in the text in front of it, and its details and the arrows sit above the player.
- A tag has a colour and, if you want, an icon. You choose them where you create the tag, and change them in Manage tags, where tags can also be renamed, merged and deleted. A change reaches the meetings you can read; meetings in rooms you cannot open keep the tag as it was. Colours are stored for the installation rather than inside the recordings, so recolouring a tag rewrites nothing.
- Each AI provider now carries a default model, set in AI providers. Summaries and insights use it unless the step names its own, and the Prepare panel's model field opens pre-filled with it, so a run can use another model without picking one every time.
- A failed insight can be retried from its card in the browse list and from its document, not only from the panel that started it. A failed run now records only a reason (`reason` on the run, one of fourteen tokens); the app decides the wording, so the words can improve without touching stored runs.
- **One dialog, once per install.** The first administrator to open a fresh Cassini is told that recordings, and the names of the rooms they came from, will be visible to anyone with an account on this Nextcloud, and given one button that creates the `cassini` Nextcloud account they are kept in. Nextcloud asks them to confirm their password, and Cassini never sees it; the account's own password is generated, set and discarded. The dialog is recorded as seen by the install rather than by the browser, and only once the account exists: an administrator who leaves it to change the audience first is asked again next time, and so is one whose install cannot create the account at all — where Cassini cannot create it, the dialog says so and points at Operator › Settings instead of claiming to be ready to record. On Nextcloud releases that let an app write to user administration, Cassini creates the account when it is enabled and nobody is asked anything.
- **Operator › Settings › "Who can see recordings"**, with two audiences and one sentence each: **Everyone with a Nextcloud account** and **Meeting participants**. ### Changed
- Skip standalone recorder integration jobs on PRs confined to the operator, frontend, microsite, or PR-conflict automation. Shared and unknown inputs still run the scenarios, and main pushes retain full coverage.
- **Storage that does not match the recorded audience is reported as a mismatch** that refuses to publish and names both ways out. A Team-folder list Cassini cannot read counts as an unanswered question rather than as "there is no Cassini Team folder" — the folder list arrives with every folder on the instance in one response, so a single unrelated folder in an unexpected shape used to make the whole answer undecodable and indistinguishable from an empty one.
- **Cassini no longer builds Team folders or their ACL topology on its own.** On every enable it checks what is there and reports what is not; it makes those changes only when you ask for them. A half-built setup can no longer end up looking healthy.
- **Talk refuses to start a recording when the storage it would be published to is missing a named prerequisite**, instead of capturing the whole call and failing afterwards. The moderator sees Talk's own "The recording failed" message; the reason, and the command that fixes it, are in Cassini.
- **Installing the two Nextcloud apps is the one step Cassini still cannot take for you, and it now says so** instead of implying otherwise. Nextcloud requires an administrator's password on that particular request, which Cassini declines to handle; it attempts the install through its own backend — which works on Nextcloud 32.x, 33.0.0–33.0.5, 34.0.0, and on any release where `allowed_no_password_confirmation_ranges` is set — and otherwise links you to Nextcloud's own Apps page. When the App Store refuses, the message says plainly that Nextcloud reports the same error whether the app is unknown, incompatible or the store is unreachable, and that retrying inside five minutes will say the same thing.
- **`backfill-nc-files` refuses to run where recordings are visible to anyone with a Nextcloud account**, instead of writing access rules into a folder where they mean nothing. Everything it writes is protected by Team-folder permissions, and those recordings live in the `cassini` account's own folder where every signed-in account can already read them — so the migration would be at best a no-op with side effects, and at worst would re-derive an audience for recordings an administrator had deliberately left open. The refusal names the audience, writes nothing, and points at the setting that actually moves an archive between the two.
- **The recordings-permissions, install and privacy documents now describe both audiences.** The upgrade section in particular had the Team-folder path collision backwards — a Team folder takes the `Cassini` path and Nextcloud renames the colliding home directory, rather than the mount being remapped — so its instruction to move the old folder out of the way first was unnecessary.
- A keyless OpenAI-compatible endpoint now switches meeting summaries on: `LLM_BASE_URL` alone is enough, and `OPENROUTER_API_KEY` is needed only when the endpoint requires one. Previously both had to be set, so a self-hosted model server silently produced no summary. **On upgrade**, an install that had `LLM_BASE_URL` set without a key starts producing summaries through that endpoint from its next build.
- With no key configured the recorder omits the `Authorization` header entirely rather than sending an empty bearer token, which some self-hosted servers reject. New request bounds for slow local models: `CASSINI_LLM_TIMEOUT_SEC` (default 900) and `CASSINI_LLM_MAX_TOKENS` (default 4096).
- `cassini meetings search` says where a speaker id comes from — the `speaker=` value a previous result printed — so `--speaker` can actually be used. The ids are opaque and are not meant to be typed from memory.
- **The control panel names each recording after its conversation.** A recording was labelled by its room token — `Call 3qbs6123vxx` — which identifies the call but not which conversation it was. Rows and the detail heading now show the Talk conversation's display name wherever the operator has it, keeping the token label as the fallback for a non-Talk recording, one whose room-name lookup never completed, and anything recorded before this release.
- Opening a meeting slides it in over the list from the right, instead of replacing the list with a second column; on a phone it arrives as a bottom sheet. Close it with the × or Escape, and the list is still there, in the same place, with the same room selected.
- The search box moved to the top of the list and filters within the selected room. It still matches a meeting's name or date, and the room and search narrowings each show as a chip you can clear.
- A word can now be flagged `lowConfidenceSpeaker` only when its own track sits well below that speaker's own speech level (the quiet-owner signature). Genuine double-talk between microphones with different signal-to-noise ratios measures large gaps but is never flagged, and the crosstalk threshold is estimated on the quiet-owner population alone. The per-word `attributionGapDb` measurement itself is unchanged and still annotates every word.
- The meeting manifest records what the attribution stage did: whether it ran, the mode (annotate/drop/disabled), words measured, flagged and dropped, and the estimated threshold when one was found. A build that deletes words in drop mode is no longer indistinguishable from one that never saw them.
- `CASSINI_STT_BACKEND`, `CASSINI_ATTRIBUTION_DISABLED` and `CASSINI_ATTRIBUTION_DROP` are documented and passed through the deployment bundle; an unknown backend id now fails the build before any decoding or model download instead of after the mixdown.
- `CASSINI_ATTRIBUTION_DROP=1` removes flagged crosstalk words from the transcript itself instead of only marking them, and `CASSINI_ATTRIBUTION_DISABLED=1` skips the measurement. Marking is the default: real crosstalk overlaps the level range genuine simultaneous speech occupies, so deleting canonical words on a threshold is opt-in.
- The word being spoken now lights up instantly instead of fading in. The fade lasted about as long as a short word, so the highlight was always part-way through changing and never quite agreed with what you were hearing; it now tracks the audio exactly. Hovering a word to seek also highlights it immediately.
- Overlapping speech reads as speech again. A turn is now one paragraph, however many pieces the producer cut it into: when two people talk over each other their sentences no longer alternate in one-to-three-word fragments. A short reaction someone made while another person was talking appears as a quiet chip where it happened, inside the sentence it landed in, and a turn that genuinely ran over another says so by naming the other speaker.
- Durations are gone from the transcript. A badge reading "0.2 s during Ivan" on every fragment was precision nobody acts on, and it made the page harder to read than no marking at all. The measurements are still there for anything that wants them; they are no longer shown.

### Fixed
- Manifest validation now rejects environment overrides whose names appear only outside environment declarations or inside XML comments, preventing AppAPI from silently dropping those values.
- Tagging a selection of meetings now uses one atomic database batch and displays all updated rows together. Safe retries reuse the batch request ID; recordings continue syncing individually across the archive workers.
- CI no longer fails when a third-party apt repository preinstalled on GitHub's runner image serves a bad package index. Every workflow install step now runs `scripts/ci-apt-update.sh`, which drops apt sources that are not the Ubuntu archive before updating, so a vendor we never install from cannot take a build down. On 2026-09-09 a corrupt Google Chrome index turned nine jobs across four workflows red on `main` with `apt-get update` exit 100; the previous remedy named `packages.microsoft.com` at three of the nine call sites, and this replaces it at all of them.
- **Restarting the Cassini container no longer stops it publishing until an administrator disables and re-enables the app.** Cassini checked how Nextcloud is set up on the app's enabled edge, and that check was the only thing that could mark the storage usable — so a plain restart left it reporting an unknown state and refusing to publish, with nothing obviously wrong. It now re-checks at startup as well, for installations that have already recorded which storage model they use. A first install is unaffected: Nextcloud rejects the calls until registration finishes, so that case still waits for the enabled edge, which fires moments later.
- `cassini-operator backfill-search` now indexes recordings this Cassini has no local copy of, by reading the published recording itself. Before, a meeting whose job record or working copy had been lost — which is every meeting published by an earlier installation, since the recordings outlive the app's own volume — was skipped entirely and silently absent from search. On the demo archive that was 25 of 30 meetings. Those are indexed at coarser granularity, and each result says which kind it is.
- `cassini-operator backfill-search` now verifies a local transcript against the checksum the archive itself records for the delivered recording, instead of a digest from the job database that could never disagree with the local copy. A meeting whose local transcript belongs to a re-run that never published is detected and indexed from the published recording instead, so search only ever cites words that are in a recording you can play.
- A read failure during `backfill-search` — a timeout, a busy Nextcloud — no longer removes a meeting's existing search entries. It is reported as failed and re-running is the fix; entries only change on evidence about the recording itself.
- `backfill-search` no longer reads the job database at all, so it can run while the operator is publishing; the old database-is-locked failure is gone. Where the delivery recorded a checksum, a re-run now confirms an unchanged meeting with one metadata query instead of re-downloading the recording.
- Speaker attribution now calibrates a participant's noise floor across all of their packet streams. A rotation or rejoin produces a fresh stream, and a short one carrying only ongoing speech had that speech as its own floor — so the real speaker measured as barely audible and a quiet track carrying only their bleed won the word by 20 dB.
- Words keep their attribution provenance through LLM readable cleanup, so summaries actually exclude probable crosstalk. Readable cleanup and summarisation normally share one configured model, so losing the flag there made the summary protection a no-op in exactly the ordinary path.
- Filtering no longer discards older segments that carry text but no word list.
- A participant's noise floor is now the quietest floor any of their streams established, rather than a percentile over their pooled frames. Pooling was duration-weighted, so a long speech-only rejoin swamped the short stream that had actually seen the microphone idle, and crosstalk beat the real speaker again.
- Readable cleanup maps each rewritten word to the single best-overlapping source word, so one contradicted word can no longer flag a legitimate neighbour and delete it from the summary.
- Portable meetings now carry the per-word attribution evidence: `cassini pack` copies `attributionGapDb` and `lowConfidenceSpeaker` from `transcript.words.v1.json` into the portable transcript items (and `cassini extract` writes them back out) instead of stripping them from the published `.opus`.
- The synthetic meeting generator now slides a turn that starts before the same speaker's previous one has finished, instead of aborting the whole run. Aborting happened partway through, leaving earlier participants generated and later ones missing — which is how the committed showcase fixture ended up with real speech for only two of its six speakers.
- Transcription tests now build meetings with production's shape — late-joining tracks, DTX-sparse tracks, and rejoined streams sharing one participant id — instead of tidy tracks that all start together and are fully dense. The previous fixtures could not express the conditions that two thirds of production streams actually have.
- The meeting list and header now show the date the meeting was recorded, not the date its file was last processed. Reprocessing an archive no longer restamps every meeting with the rebuild day.
- Meeting list cards now show the meeting's start time alongside its date.
- The viewer now shows when two people spoke at once. Overlapping speech used to render as ordinary consecutive paragraphs with no signal at all, and because a turn is cut at every speaker change, a listener's "right" in the middle of someone's sentence split that sentence across two paragraphs with an unrelated turn wedged between them — so a continuous utterance read as two turns and an interruption. An interrupted turn is now drawn as one turn containing the interjection, each turn carries a badge naming who it overlapped and for how long, and playback highlights every turn that is sounding rather than only the latest one to start.
- Overlap is judged on the words that actually sound rather than on paragraph extents, and a word whose end ran past its own audio is pulled back before anything is drawn. Without that, meetings recorded before the timing fix would light up with overlap that never happened: across nine archived meetings their paragraphs intersect for 94.2 s while their words only sound together for 15.7 s. A meeting whose recording already measured where each word ends says so in its own file, and the viewer leaves its timings exactly as recorded — so a word somebody genuinely held for a second and a half stays that long.
- A word now ends where its speaker's own audio ends. Parakeet stamps a trailing punctuation mark at the *next* acoustic onset, and the token-to-word conversion took that mark's timestamp as the word's end — so a sentence-final word could run for seconds while its speaker was silent, and across whoever spoke during that pause, which the viewer then drew as an overlap that never happened. The mark still travels in the word's text; it no longer decides the word's extent. Instead the energy gate that already decides whether a word is real follows the speaker's own track forward from the last spoken token and stops at the last active 10 ms of it, bridging a silence of up to 200 ms as a stop closure inside the word. A word built entirely from punctuation carries no audio of its own and is never extended, and no word may pass the end the old rule gave it. Measured against unmodified `main` on a 36-minute three-participant meeting (5549 words, the production fp32 model), the longest word falls from 4.07 s to 1.44 s and cross-speaker overlap stamped over a silent track from 4.18 s to 1.69 s, against 1.37 s of audible speech given up across the whole meeting, two words of it losing 100 ms or more. Those are whole-release totals; the final refinement alone — dropping an 80 ms grace after the last active frame — accounts for 0.38 s of that speech and for no word losing 100 ms.
- Playing a long meeting no longer pins a processor core. The viewer rebuilt the entire transcript's highlight sixty times a second and re-checked every word on screen in order to move one of them, so on the longest published meetings playback ran at about twenty frames a second, the page stuttered while scrolling, and the highlight visibly trailed the audio it was meant to track. The highlight is now worked out once per transcript and touched only when the playhead actually crosses a word, which took the worst meeting in the archive from using most of a core to using under a tenth of one, at a steady sixty frames a second. Clicking a word to seek costs about half what it did on the same meetings. The longer you listened the worse it got, too: playback accumulated duplicate timers until it was running forty-four clocks where one was needed, so a five-minute listen was heavier per second than a one-minute listen. Memory and timer count now stay flat — measured over a continuous five-minute listen on the largest meeting.
- A long answer is paragraphed again. Rebuilding a turn from the pieces the producer cut also undid the breaks it makes when somebody talks for a while, so one standup update rendered as a single 209-second block of text (the longest rows on that meeting were 209 s, 101 s and 97 s against a median of 8.7 s). The reading unit now follows those breaks where nothing came between two of the speaker's blocks, and overrides them only where somebody else's speech cut a sentence in half, which is the case this rebuilding exists for. Same meeting: longest row 58 s, median 10.4 s.
- A quick back-and-forth is no longer folded into one turn. Rebuilding a speaker's turn now needs the person who spoke in between to have actually overlapped or touched it: if they said their piece in clean air and stopped, both people kept their own turn, in the order they spoke. Without that, five real turns of a fast exchange collapsed into one row with an answer rendered before the question it answered.
- Playback follows the paragraph it is reading. It used to follow whichever producer fragment was sounding, so during two people talking over each other the page smooth-scrolled between the pieces of the same rebuilt paragraph every few hundred milliseconds.
- The "probably crosstalk" warning is judged once over everything a turn actually said, instead of once per fragment. One flagged fragment no longer condemns a whole genuine turn, and a short reaction that is entirely flagged keeps its warning now that it renders as a chip.
- The viewer now shows the meeting summary the recorder seals into the portable `.opus`. The summary was already inside the file (the `summary.md` attachment that `cassini meetings` reads), but the web viewer and the in-Nextcloud app never displayed it, so a meeting with a summary opened as transcript-only. It renders as Markdown in the existing Summary panel; a file without one, or with a damaged attachment, still opens without a panel rather than failing.

### Changed
- **A recording's room is now recovered from the operator's own job history rather than guessed from its file name.** The catalog entry's id is the job id, and `jobs.talk_binding` still holds the Talk room token for every job the operator ran — so `scripts/backfill-catalog-rooms.sh` derives the real room id for anything this installation produced, and falls back to a name-derived id only where no job row survives. Re-running it merges rooms an earlier pass split in two.
- **Both maintenance scripts now re-tag the published `.opus`, not just `catalog.json`.** The exporter re-derives a catalog entry's room from the file on every republish, so a catalog-only change was silently undone by the next re-seal. Pass `--no-retag` to keep the old behaviour and accept that the change is temporary.
- **`scripts/reattribute-catalog-room.sh` refuses to move a meeting the operator has a recorded room binding for** (new exit code 5, `--force` to override), including in a dry run. For those meetings the real room id is recoverable and the backfill is the correct tool; asserting a different one would leave a recording whose lineage and published room permanently disagree.
- **A room that got split in two is repaired by re-running the backfill, not merged by hand.** 0.2.0-beta.2 said a split — from a pepper rotation, or from a recording made before that release — stayed until you merged it yourself. Re-running `scripts/backfill-catalog-rooms.sh` now re-derives every meeting whose job row survives and closes the split; only recordings imported from elsewhere still need `scripts/reattribute-catalog-room.sh`.
- **A meeting's room name now lives in `catalog.json`, not in the recording.** 0.2.0-beta.2 announced the display name as something the portable `.opus` carries; it no longer does — the file carries the room id, and the operator writes the name into the catalog on every publish, preserving it across a republish. A display name is editable and a sealed recording is not, so honouring a rename used to mean rewriting every file that room ever produced; it is now one edit in a file that is rewritten anyway. The stamped name is the one that job recorded, not the room's current name — a republish restamps the same value — so what this buys is the ability to correct a name, not a name that follows Talk. The name at record time is still in the file, as the meeting title.

### Fixed
- A publish interrupted partway no longer leaves an unprotected recording behind: the next publish denies, removes and re-creates it.
- A re-publish no longer resets a recording's access rules, so permissions changed by hand in Nextcloud Files now survive it.
- An interrupted upload is no longer published as a silently truncated recording; the delivery fails and can be re-run.
- A publish now fails instead of rewriting the archive when the meeting index cannot be read. A server error answered with a JSON body used to read as "this archive is empty", which replaced every meeting in the index with the one being published.
- A room recovered by the backfill no longer reverts the next time its meeting is re-sealed or republished.

### Security
- Recordings are now given their access rules before they hold any audio. A recording used to be uploaded first and made private in a second request, so it was readable by every account on the instance in between — and permanently readable if that second request failed.
- The meeting index gets the same treatment, in both places that write it: the one-shot Nextcloud Files migration used to upload the index of every migrated meeting — titles, room names, dates — before locking it to the owner.

### Added
- **Data-processing & privacy note.** A new `docs/privacy.md` documents what
  Cassini stores, where it lives, the single optional step (LLM cleanup and

- The App Store listing now shows what Cassini is: screenshots of the meeting viewer and the admin control panel, an `ai` category alongside `integration`, and user/admin documentation links. A screenshot-less entry reads as abandoned; the listing now presents the product.
- **Meetings now know which conversation they came from, and you can list and filter by it.** Until now a recording's room name was flattened into its title and the room's identity was discarded, so there was no way to ask for "the meetings from this room". Every recording made from here on carries a room id and display name in its portable `.opus` and in the published catalog, and the CLI gains two ways to use that: `cassini meetings rooms` lists the conversations your account has readable recordings from, and `cassini meetings list` accepts `--room`, `--from` and `--to` (all optional, and they combine — `--from 2026-08-01 --to 2026-08-31` means all of August). The agent skill for reading meetings now narrows by room and date before listing, instead of fetching the whole archive and guessing.
- **A new setting, `CASSINI_ROOM_ID_PEPPER`.** The room id published on a meeting is a one-way derivation of the Talk conversation's identity, never the conversation's own token — for a public conversation that token is also the link that joins it, and every signed-in account can read those recordings. Setting this to a stable secret is what makes the derivation resistant to being reversed: a Talk token is short enough that an unpeppered one can be recovered by working through the possibilities offline. Choose it once — changing it changes every room id, and meetings already published keep the ids they were written with, so a room splits in two until you merge it again.

### Changed
- The Nextcloud App Store description now discloses that recording and
  transcription stay on your infrastructure and that only the optional
  external-LLM step sends data to a third party.
- **Recordings published before this update can be given their room back, from the files themselves.** Run `./scripts/backfill-catalog-rooms.sh` once, by hand, on the host where the app container runs; it reports what it would change and writes nothing until you add `--apply`. It recovers each meeting's room name from its published recording and derives a room id from that name, because those files never carried the conversation's token and it cannot be recovered from them.
- **Because of that, one conversation can appear as two rooms** — one identified from its token, for recordings made since the update, and one identified from its name, for everything older. Cassini cannot prove they are the same conversation: two conversations can share a display name, and a room can be renamed between recordings. When you know they are the same, `./scripts/reattribute-catalog-room.sh --from <id> --to <id>` merges them, and like the backfill it shows you every meeting it would move before it writes anything.

### Fixed
- **Published recordings can be deleted again.** Cassini created its `Cassini` Team folder with a Group Folders flag that, on recent versions, made every file in it permanently undeletable and un-moveable — by everyone, including the Cassini account and Nextcloud administrators. New installations no longer set it, and nothing else changes: who can read a recording is decided by the same per-recording permissions as before. An existing folder cannot be repaired automatically, because Group Folders offers no way to clear the flag after creation; the app's status page now reports the condition and what it costs instead of leaving it invisible.
- **Setting up recordings no longer fails on an installation that is already correct.** On a Nextcloud that requires password confirmation for administration, an administrator has to create the recordings folder by hand — after which Cassini re-applied the same group and permission settings anyway, was refused, and reported the setup as broken even though nothing was wrong. It now checks what is already in place and only writes what is missing.
- The app's status page no longer reports a completed setup as healthy when a step failed along the way.
- **Setting up the recordings folder now reports why it failed.** The Group Folders API answers a refused request with `HTTP 200` and the failure recorded only inside the response body, so Cassini read a refusal as a success and then failed while decoding it — reporting a JSON error that named neither the problem nor the cause. On Nextcloud installations that require password confirmation for administration, every one of these requests is refused, and the app's status page said only that setup was incomplete. Cassini now reports the actual reason and, when it cannot proceed, names the `occ` commands that create the Team folder by hand — which it then adopts on the next enable.
- **Setting up recordings no longer fails on Nextcloud installations that require password confirmation for user administration.** Cassini creates a `cassini` service account and its group when the app is enabled; on Nextcloud 34 (and any instance enforcing password confirmation) those calls are refused, because an app has no browser session in which to confirm a password. An administrator can create the account and group by hand — but Cassini did not check whether they already existed before trying to create them, so a correctly prepared installation looked identical to an empty one and setup failed permanently. Cassini now looks first, adopts what is already there, and when it genuinely cannot proceed it names the `occ` commands that fix it.

Setup work — creating the recordings folder, its groups and the service account itself — is still performed as an administrator; storing and reading recordings is not. The account owns and serves the recordings; there is no other mode.

Recordings are owned by a dedicated `cassini` service account, which also manages their ACLs; privileged setup is performed separately as a Nextcloud administrator. Because the audience group is virtual, every account has the mount from the moment it is created — there is no membership sweep and no convergence delay. Two native prerequisites remain, neither of which an external app can install for itself: the Group folders ("Team folders") app and the Everyone Group (`group_everyone`) app. The local harness enables both automatically.

The two Nextcloud apps Cassini cannot install for itself — Team folders and Everyone Group — are now checked by name before setup starts, and reported individually.

Existing installs pick the route up when the app is next registered or updated.

The migration changes nothing when Nextcloud Files already holds recordings, or when there is no older archive to move, so it is safe to run when you are unsure whether it is needed — and skipping it entirely is a supported choice: the old recordings simply stay where they are and everything published from now on works normally.

- Setup no longer assumes the administrator is called `admin`. Cassini probes for one — the configured account, then `admin`, then the instance's own account list — so instances that name theirs differently can complete setup. If none of them is an administrator it says so and stops, rather than continuing as an account that may not exist; `CASSINI_NC_ADMIN_USER` names one directly.
- Publishing a recording no longer rewrites the whole Nextcloud Files archive. Each publish uploads its own recording and adds it to the shared catalog, so a delivery that fails can no longer remove other meetings from the list.
- A recording you are not allowed to see now reads as "not found" rather than "forbidden". Reporting a denial told you the recording existed, which is exactly what the access model is meant to prevent. Genuine outages are still reported as errors, and denials are still distinguishable in the operator's logs.
- The internal site manifest (`cassini.json`), which lists meeting counts and job ids, is no longer readable by any signed-in user of an installed app.
- The viewer no longer treats an unreachable meeting list as an empty one. A Nextcloud outage now surfaces as an error instead of an empty archive.
- **Recordings of public conversations are now readable by everyone, as you would expect.** A conversation anyone with the link can join was treated exactly like a private one, so its recording was restricted to whoever happened to be on the attendee list. That was worst for the most public meetings: participants who joined by link rather than by invitation cannot be granted access individually, so a public meeting full of link guests produced a recording only its owner could open. Recordings of public conversations are now visible to any account on the Nextcloud.
- **A newly created user can now see public recordings straight away.** The recordings Team folder now uses Nextcloud's virtual `everyone` group, so every account has its mount from creation instead of waiting for a periodic membership sweep. A new account sees everything it is entitled to on its first Cassini visit.
- **A public recording no longer loses its broad access when the app restarts.** A periodic integrity sweep re-applies the restrictive permissions to any recording that is missing them, and it mistook a public recording's deliberately broad grant for a missing restriction — quietly turning every public recording back into a participant-only one. The sweep now leaves a recording's own permissions alone, whichever way they were set, and only repairs recordings that carry none at all.
- **A momentary Nextcloud Talk hiccup no longer costs a recording.** Working out who a meeting belongs to happens once, at publish time, and now gates publishing — so a single failed request used to fail the recording outright, recoverable only by re-running the job by hand. The lookup now retries, and then falls back to asking as the recordings owner, which is the case retrying alone cannot fix: the person who started the recording may have left the conversation, been removed or been disabled between the meeting and its publication. A meeting whose participants are all guests or federated users still publishes successfully and stays visible to its owner only.
- **The recordings list no longer gets stuck on "Meeting not found".** Opening the viewer before its first recording exists — or during any brief Nextcloud hiccup — could leave the right-hand pane showing an error that stayed there even after the list loaded, until you clicked a meeting or reloaded. A link to a specific meeting opened in that window was also dropped instead of opening once the list arrived.
- `bin/cassini` no longer leaks a ~17 MB temp directory on every invocation (about 3.7 GB/day on a dev VM running the harness). The wrapper now builds the CLI to a stable path under `${XDG_CACHE_HOME:-$HOME/.cache}/cassini/bin` and reuses it, so there is nothing to clean up; concurrent invocations stay safe via an atomic rename, on macOS too.
- **A recording is no longer published before its downloadable meeting file exists.** The portable `.opus` — the single-file meeting you download, share and archive — used to be produced in the background *after* the recording had already been handed off for publishing. If that step failed, was interrupted by a restart, or was overtaken by a second run of the same recording, the recording could still be reported as finished while its meeting file was missing, stale, or belonged to a different run. Packing that file is now a stage the recording has to pass: it is written once, checked, and fingerprinted before publishing starts, and the file that reaches the viewer is verified to be that exact file. A failure now fails the recording, with the reason recorded and a rerun available, instead of disappearing into the log.
- **Re-running a recording can no longer overwrite the previous run's meeting file.** Each run now writes its own, so the two cannot race.
- **A failed publish can no longer leave the recordings page without its viewer.** Refreshing the site's viewer files used to delete them before copying the new ones in; an interrupted copy left the page listing recordings it could no longer play. The new files are now staged beside the old ones and swapped in, so a failure leaves the previous, working page exactly as it was.
- **An interrupted replacement can no longer destroy a meeting file.** `cassini pack` removed the previous `.opus` before moving the new one into place; it now replaces it in a single atomic step.
- **Setup no longer assumes the administrator is called `admin`.** Cassini used to look up the administrator with a request made *as* the administrator it had not found yet, so on an instance whose administrator is named anything else the lookup failed, it carried on as `admin` regardless, and every subsequent step was rejected with nothing explaining why. It now asks Nextcloud who the accounts are and finds an administrator among them; if it cannot, it stops and says so, naming `CASSINI_NC_ADMIN_USER` as the way to point it at one.
- **A recording whose permissions could not be applied is no longer reported as published.** Nextcloud accepts a permission change on a file outside a Team folder with a success code that hides a per-property rejection, so the recording could be stored with no restrictions at all while everything looked fine.
- **An administrator whose install was broken no longer loses the Operator surface.** Cassini decides whether to show the operator by asking the admin-only status endpoint, and that endpoint answers 503 when recordings cannot be served — which was being read as "not an administrator". The one person who could fix the install saw the same browse-only app, and the same unexplained error, as everyone else.
- Catalog meeting dates now come from the pack's recorded `createdAtUtc` (rendered in UTC), so meetings whose file name carries no timestamp — e.g. backfilled dailies — show a real date and sort correctly instead of echoing the raw id. Already-published archives pick this up on their next export.
- Portable-meeting documentation was brought back in line with the format emitted by that release.
- **A recording delivered to Nextcloud Files is now verified to be the file the recording actually produced.** Cassini fingerprints each meeting when it is packed and re-checks that fingerprint before publishing; the check was applied when recordings were stored on the app's own volume, but not on the Nextcloud Files path an installed app uses. A recording whose file does not match what was packed is now refused before anything is uploaded, so a half-delivered recording can no longer appear in the archive.
- The standalone operator container no longer risks clearing more than its own site directory when started with an unusual `CASSINI_OPERATOR_SITE_ROOT`.
- The recordings migration script (`backfill-nc-files.sh`) now runs on macOS's system bash, where invoking it with no options previously aborted.
- The local test harness now stops with a clear message when Nextcloud Talk fails to install, instead of continuing and failing much later with an unexplained error.
- Fixed harness startup under the macOS system Bash when optional Compose or Nextcloud command arguments are empty.

- Reworked the viewer to load meeting data through a single `DataProvider` seam instead of hardcoded static fetches, decoupling the viewer UI from its data source (groundwork for unifying the viewer and operator into one in-Nextcloud app). No user-visible behaviour change.

Every logged-in user gets the meeting-browsing app; the operator/recording-control surface returns as an admin-gated surface *inside* the one app in a follow-up (D-420 V3), and the operator JSON API stays admin-only throughout (unchanged security boundary). No change for viewer users.
- Split the in-Nextcloud viewer into a shell (`App`) plus reusable `MeetingList` and `MeetingView` components — the app-shell layer for unifying the viewer and operator into one in-Nextcloud app (`MeetingView` is also the future standalone single-meeting share surface). - Reworked the Cassini operator panel for the in-Nextcloud audience it is now shown to: the recordings list and run detail work as a master/detail pair, each run's attempts collapse into accordions so a long retry history opens at a readable summary, starting a recording is an on-demand composer rather than a permanently parked URL field, and the API-implementation captions are replaced with plain descriptions.

### Fixed
- Fixed harness teardown and bring-up edge cases so repeated runs no longer leave stale containers/networks or duplicate `signaling-public-proxy` aliases.
- Cassini shell polish (D-420 review follow-ups): switching between the **Browse** and **Operator** surfaces now keeps the open meeting in the URL (deep-link no longer dropped); the operator surface uses the same light/dark theme as browse (stored preference, then OS) instead of only the OS setting; and the in-Nextcloud mount targets the innermost `#content` more robustly.
- Added the missing `operator/settings` proxy route so the operator surface's STT-quality Settings panel works through the Nextcloud AppAPI proxy (it previously had no route and would have 403'd/404'd), and dropped the now-dead `control-panel` proxy routes left over from the collapsed second entry.
- Talk recorder: stabilized subscriber negotiation behind intermittent empty/blank recordings ("no remuxable streams found in session artifact", silent MKVs, and 0-word transcripts). A fresh in-call participant previously caused two empty-SID `requestoffer` messages; the second could make the MCU tear down and recreate its Janus subscriber, rotating the SID while the first offer was still being answered. Initial and exhausted-peer recovery now issue exactly one request, repeated in-call snapshots keep the valid response throttle, and inbound offers cannot trigger recovery in front of themselves. The recorder also sends its answer without waiting for full ICE gathering, queues trickled candidates behind the matching answer, and emits end-of-candidates only after gathering completes (D-454).
- Stopping a recording no longer fails with "job is not stoppable" when the operator has just reported the job as running. The stop registration now brackets the whole time the job is advertised as recording, so a stop is accepted from the moment the job goes running until it leaves the record stage, and one arriving before the recorder has finished starting up is delivered as soon as it does.
- A stop requested after the recording has already ended on its own (while the operator is still uploading to Talk and queueing the build) is now accepted and recorded as a stop request instead of being rejected; the job's stop reason continues to report why the recording actually ended.
- The release pipeline's required "Faithful installed ExApp" gate now decides whether to run from a deny-list (run unless a change is purely docs/notes/assets) instead of an allow-list of enumerated product paths, so a pull request touching a build input nobody thought to enumerate can no longer report the required check green without actually building and recording.
- Talk recorder: closed two gaps that could still lose media on a call the recorder appeared to be recording normally. A participant whose handshake completed but whose media never arrived was left untouched for up to ~45 seconds, so short calls (a ~30s 1:1) could still finalize as empty ("no remuxable streams"); such a peer is now rebuilt about 12 seconds after its answer, but only while its connection is not actually established, so a slow-but-healthy participant is never torn down. A participant who turned their camera on mid-call could also be wedged permanently by a dropped signaling answer — their audio kept recording while the newly added video was silently lost for the rest of the call; the recorder now retransmits that answer as the signaling connection recovers, within a bounded budget, instead of skipping the participant forever (D-509).
- Fixed the CI session-artifact guard passing recordings that captured no media. It verified headers and index framing but never counted packets, so a capture with a valid header and a 0-byte index reported "session artifact verification passed" — the exact empty-capture class (D-454) the per-PR e2e leg is relied on to catch. The guard now walks each stream log and requires real RTP media packets per captured stream, counted kind-aware so a stream carrying only RTCP no longer passes for having non-empty bookkeeping.
- Fixed the A/V drift check reporting success without measuring anything. It exited 0 when no audio/video pair was found, and also when pairs were found but every one was too short to compare — printing "av drift check passed" after zero comparisons. Drift runs now require at least one pair to be actually compared, and the rejoin leg, which legitimately records video-less, opts down explicitly.
- Fixed the e2e leg never producing a drift pair the check could measure. The publisher bots play the sample fixture once and stop at its end, and the default fixture is 15s — capping the measurable pair at ~11s against the 15s minimum regardless of the configured publish window. The leg now prepares a fixture sized to the publish window. The fixture is also rendered with a keyframe at least every 0.5s (libvpx's default 128-frame interval delayed decodable video up to ~4.3s behind audio, which the elapsed-difference metric misread as drift), and the leg's tolerance carries a documented budget for the remaining structural skew.
- Fixed panels, cards and form fields losing their borders and shadows inside Nextcloud, which left content areas with nothing to separate them.
- Fixed high-contrast themes leaving those same areas undefined, and the selected recording unmarked.
- Fixed Nextcloud's app chrome applying twice, which added a second header-height gap, doubled the side margins, and clipped the bottom of the app.
- Fixed the shell tab bar, the operator scrollbar gutter, and the detected-hardware values rendering with the wrong colours under some themes.
- Fixed the recordings list not appearing on narrow screens.
- Fixed the settings Save button offering to save when nothing had changed.
- Fixed the meeting filter drawing a second focus ring inside its own.
- Fixed the meeting load-in fade stalling and then snapping into place.
