# Changelog

All notable user-facing changes to Cassini will be documented in this file.

This project follows semantic versioning for Nextcloud App Store releases.
The version in `appinfo/info.xml`, the ExApp Docker image tag, and the release
archive version must match.

## [Unreleased]

Unreleased changes are collected as fragments in `changelog.d/`. Versioned
sections below are script-managed: `scripts/fold-changelog.sh` (run by
`scripts/prepare-release.sh`) folds those fragments into this file under the new
version and removes the consumed fragments. Edit released sections only to fix
mistakes; add new entries as fragments. See [`docs/release.md`](docs/release.md).

## [0.2.0-beta.4] - 2026-08-28

### Changed
- **GPU transcription upgrade:** existing portable/plain-image ExApp installations continue to capture and preserve Talk audio, but operator-managed transcription now enters `build/blocked` instead of using CPU ASR. Install the matching `-cuda` image on a GPU deploy daemon, then choose **Rerun** for each preserved blocked job in Cassini Admin.

### Fixed
- Short interjections now retain their real timeline position and speaker attribution. Transcription drains final VAD audio, recovers more subsecond turns, and rejects near-silent decoder hallucinations without discarding speech whose decoded timestamp leads its waveform.
- Transcript construction no longer applies duplicate timeline offsets or retains both sides of a mixed-track fallback, and genuine final words emitted in decoder or VAD padding are preserved at the real audio boundary.
- Meeting duration now comes from playable audio without discarding source-container provenance or preallocating PCM from corrupt duration metadata.
- GPU readiness failures are reported explicitly, and generated artifacts record the effective ASR device.

## [0.2.0-beta.3] - 2026-08-28

### Added
- `cassini retag` rewrites an already-packed `.opus` file's room and job fields without re-encoding its audio, verifying the result against the manifest's own PCM digest before writing it. It is what lets a recovered room survive a republish, and what the maintenance scripts below use.
- A meeting's portable `.opus` now records which operator job and attempt produced it (`meeting.jobId`, `meeting.attemptNumber`, mirrored as `CASSINI_JOB_ID` and `CASSINI_ATTEMPT_NUMBER`). Both are optional; a file packed outside the operator has neither.
- `cassini inspect` prints an `origin` line with a portable file's room, job and attempt — previously it decoded the room and printed nothing, so checking the producer chain by hand meant a raw `ffprobe`.
- `cassini meetings context` includes the room the meeting came from, in both the markdown and the `--json` form.
- `scripts/backfill-catalog-rooms.sh` gains `--jobs-db PATH`, `--no-jobs-db` and `--no-retag`; `scripts/reattribute-catalog-room.sh` gains `--force`, `--jobs-db PATH`, `--no-jobs-db` and `--no-retag`.

### Changed
- **A recording's room is now recovered from the operator's own job history rather than guessed from its file name.** The catalog entry's id is the job id, and `jobs.talk_binding` still holds the Talk room token for every job the operator ran — so `scripts/backfill-catalog-rooms.sh` derives the real room id for anything this installation produced, and falls back to a name-derived id only where no job row survives. Re-running it merges rooms an earlier pass split in two.
- **Both maintenance scripts now re-tag the published `.opus`, not just `catalog.json`.** The exporter re-derives a catalog entry's room from the file on every republish, so a catalog-only change was silently undone by the next re-seal. Pass `--no-retag` to keep the old behaviour and accept that the change is temporary.
- **`scripts/reattribute-catalog-room.sh` refuses to move a meeting the operator has a recorded room binding for** (new exit code 5, `--force` to override), including in a dry run. For those meetings the real room id is recoverable and the backfill is the correct tool; asserting a different one would leave a recording whose lineage and published room permanently disagree.
- **A room that got split in two is repaired by re-running the backfill, not merged by hand.** 0.2.0-beta.2 said a split — from a pepper rotation, or from a recording made before that release — stayed until you merged it yourself. Re-running `scripts/backfill-catalog-rooms.sh` now re-derives every meeting whose job row survives and closes the split; only recordings imported from elsewhere still need `scripts/reattribute-catalog-room.sh`.
- **A meeting's room name now lives in `catalog.json`, not in the recording.** 0.2.0-beta.2 announced the display name as something the portable `.opus` carries; it no longer does — the file carries the room id, and the operator writes the name into the catalog on every publish, preserving it across a republish. A display name is editable and a sealed recording is not, so honouring a rename used to mean rewriting every file that room ever produced; it is now one edit in a file that is rewritten anyway. The stamped name is the one that job recorded, not the room's current name — a republish restamps the same value — so what this buys is the ability to correct a name, not a name that follows Talk. The name at record time is still in the file, as the meeting title.

### Fixed
- A publish interrupted partway no longer leaves an unprotected recording behind: the next publish denies, removes and re-creates it.
- A re-publish no longer resets a recording's access rules, so permissions changed by hand in Nextcloud Files now survive it.
- An interrupted upload is no longer published as a silently truncated recording; the delivery fails and can be re-run.
- A publish now fails instead of rewriting the archive when the meeting index cannot be read. A server error answered with a JSON body used to read as "this archive is empty", which replaced every meeting in the index with the one being published.
- A room recovered by the backfill no longer reverts the next time its meeting is re-sealed or republished.

### Security
- Recordings are now given their access rules before they hold any audio. A recording used to be uploaded first and made private in a second request, so it was readable by every account on the instance in between — and permanently readable if that second request failed.
- The meeting index gets the same treatment, in both places that write it: the one-shot Nextcloud Files migration used to upload the index of every migrated meeting — titles, room names, dates — before locking it to the owner.

## [0.2.0-beta.2] - 2026-08-20

### Added
- **Data-processing & privacy note.** A new `docs/privacy.md` documents what
  Cassini stores, where it lives, the single optional step (LLM cleanup and
  summaries) that sends data off your infrastructure, and what deletion and
  uninstall remove.
- The App Store listing now shows what Cassini is: screenshots of the meeting viewer and the admin control panel, an `ai` category alongside `integration`, and user/admin documentation links. A screenshot-less entry reads as abandoned; the listing now presents the product.
- **Meetings now know which conversation they came from, and you can list and filter by it.** Until now a recording's room name was flattened into its title and the room's identity was discarded, so there was no way to ask for "the meetings from this room". Every recording made from here on carries a room id and display name in its portable `.opus` and in the published catalog, and the CLI gains two ways to use that: `cassini meetings rooms` lists the conversations your account has readable recordings from, and `cassini meetings list` accepts `--room`, `--from` and `--to` (all optional, and they combine — `--from 2026-08-01 --to 2026-08-31` means all of August). The agent skill for reading meetings now narrows by room and date before listing, instead of fetching the whole archive and guessing.
- **A new setting, `CASSINI_ROOM_ID_PEPPER`.** The room id published on a meeting is a one-way derivation of the Talk conversation's identity, never the conversation's own token — for a public conversation that token is also the link that joins it, and every signed-in account can read those recordings. Setting this to a stable secret is what makes the derivation resistant to being reversed: a Talk token is short enough that an unpeppered one can be recovered by working through the possibilities offline. Choose it once — changing it changes every room id, and meetings already published keep the ids they were written with, so a room splits in two until you merge it again.

### Changed
- The Nextcloud App Store description now discloses that recording and
  transcription stay on your infrastructure and that only the optional
  external-LLM step sends data to a third party.
- **Recordings published before this update can be given their room back, from the files themselves.** Run `./scripts/backfill-catalog-rooms.sh` once, by hand, on the host where the app container runs; it reports what it would change and writes nothing until you add `--apply`. It recovers each meeting's room name from its published recording and derives a room id from that name, because those files never carried the conversation's token and it cannot be recovered from them.
- **Because of that, one conversation can appear as two rooms** — one identified from its token, for recordings made since the update, and one identified from its name, for everything older. Cassini cannot prove they are the same conversation: two conversations can share a display name, and a room can be renamed between recordings. When you know they are the same, `./scripts/reattribute-catalog-room.sh --from <id> --to <id>` merges them, and like the backfill it shows you every meeting it would move before it writes anything.

### Fixed
- **Published recordings can be deleted again.** Cassini created its `Cassini` Team folder with a Group Folders flag that, on recent versions, made every file in it permanently undeletable and un-moveable — by everyone, including the Cassini account and Nextcloud administrators. New installations no longer set it, and nothing else changes: who can read a recording is decided by the same per-recording permissions as before. An existing folder cannot be repaired automatically, because Group Folders offers no way to clear the flag after creation; the app's status page now reports the condition and what it costs instead of leaving it invisible.
- **Setting up recordings no longer fails on an installation that is already correct.** On a Nextcloud that requires password confirmation for administration, an administrator has to create the recordings folder by hand — after which Cassini re-applied the same group and permission settings anyway, was refused, and reported the setup as broken even though nothing was wrong. It now checks what is already in place and only writes what is missing.
- The app's status page no longer reports a completed setup as healthy when a step failed along the way.
- **Setting up the recordings folder now reports why it failed.** The Group Folders API answers a refused request with `HTTP 200` and the failure recorded only inside the response body, so Cassini read a refusal as a success and then failed while decoding it — reporting a JSON error that named neither the problem nor the cause. On Nextcloud installations that require password confirmation for administration, every one of these requests is refused, and the app's status page said only that setup was incomplete. Cassini now reports the actual reason and, when it cannot proceed, names the `occ` commands that create the Team folder by hand — which it then adopts on the next enable.
- **Setting up recordings no longer fails on Nextcloud installations that require password confirmation for user administration.** Cassini creates a `cassini` service account and its group when the app is enabled; on Nextcloud 34 (and any instance enforcing password confirmation) those calls are refused, because an app has no browser session in which to confirm a password. An administrator can create the account and group by hand — but Cassini did not check whether they already existed before trying to create them, so a correctly prepared installation looked identical to an empty one and setup failed permanently. Cassini now looks first, adopts what is already there, and when it genuinely cannot proceed it names the `occ` commands that fix it.

## [0.2.0-beta.1] - 2026-08-14

### Added
- Cassini now makes the Talk signaling **internal secret** — the one input required for invisible HPB-internal recording that cannot be auto-provisioned — easy to know and set. When `CASSINI_TALK_SIGNALING_INTERNAL_SECRET` is missing, the operator logs an actionable `WARNING` at startup and `GET /operator/status` returns a `signaling_internal_secret_hint`, instead of only failing when a recording is attempted. The External Apps deploy-option description and `docs/exapp-install.md` now explain where to find it (e.g. `docker exec nextcloud-aio-talk printenv INTERNAL_SECRET` on Nextcloud All-in-One, or the signaling server's `[clients] internalsecret` on a standalone HPB) and how to set it.
- Zero-config Talk recording secret: `CASSINI_TALK_RECORDING_SECRET` is now optional. When it is not supplied, the operator generates a secret on first start and persists it on the AppAPI volume (surviving restart and app update), so installing Cassini from the App Store no longer requires inventing or copying a shared secret. An explicitly supplied secret still wins and is treated as externally managed.
- New ADMIN-only provisioning endpoint `operator/talk/provisioning` returns the ready-to-apply `spreed` `recording_servers` value (backend URL + secret), so an admin can register Cassini as Talk's recording backend in one step without ever handling the secret by hand.
- The operator now delivers published recordings into **Nextcloud Files**. Each published meeting's portable `.opus` is uploaded before its entry is added to the `catalog.json` index under the canonical `Cassini/Recordings/` folder. The in-Nextcloud viewer then serves its catalog and per-meeting audio authoritatively from Files (with its CSP and routes unchanged), while standalone development keeps its local source. Mutable catalog responses bypass browser caches, and the embedded viewer refreshes its meeting list on focus and every 15 seconds. Delivery failures are visible rather than silently masked by local fallback. Recordings are delivered as `.opus` only; Talk's recording `/store` endpoint (which rejects `.opus`) is not used. This first pass is public and writes as the Nextcloud admin; per-user/per-group access and a dedicated service account follow.
- **Recordings now belong to a dedicated `cassini` account, created automatically when the app is enabled.** Previously they were owned by the Nextcloud administrator, which tied every recording to a human account that may be renamed, handed over or removed, and gave the identity holding all the recordings full administrative rights over the instance. Setup work — creating the recordings folder, its groups and the service account itself — is still performed as an administrator; storing and reading recordings is not. The account owns and serves the recordings; there is no other mode.
- **Per-participant access control for recordings.** The operator freezes each recording's audience to the Talk room's participants at publish time — it grants read-only Nextcloud advanced-ACL (`nc:acl-list`) to each local participant (users, groups, circles) on the meeting's `.opus`; guests, email and federated participants are skipped. The in-Nextcloud viewer is then served **per caller**: the meeting list is built directly from `catalog.json`, filtered to the `.opus` files visible in the caller's own Nextcloud scan, and each recording is fetched as the caller so Nextcloud enforces access — a recording a user is not granted never appears and cannot be played. The read path fails closed (an empty list, never the full archive) on any error. Access is editable afterwards through Nextcloud's own sharing/ACL tools. Recordings are owned by a dedicated `cassini` service account, which also manages their ACLs; privileged setup is performed separately as a Nextcloud administrator. Two native prerequisites must be enabled first — the Team folders (`groupfolders`) and Everyone Group (`group_everyone`) apps — after which Cassini provisions the recordings folder and ACL topology itself. See `docs/exapp-nextcloud-recordings-permissions.md`.
- **Automatic setup of the recordings directory and its permissions.** Enabling the Cassini ExApp now provisions everything the model needs by itself, over Nextcloud's HTTP APIs — no manual `occ` Team-folder setup. On the enabled edge the operator creates the `Cassini` Team folder with its default-deny advanced-ACL floor, gives Nextcloud's virtual `everyone` group read and the narrow `cassini` owner group full permissions, delegates `cassini` as ACL manager, migrates any per-recording permissions left by earlier versions, applies the root container ACL (so the owner can write and every account can traverse), and creates the canonical `Cassini/Recordings/meetings` collections. Because the audience group is virtual, every account has the mount from the moment it is created — there is no membership sweep and no convergence delay. Two native prerequisites remain, neither of which an external app can install for itself: the Group folders ("Team folders") app and the Everyone Group (`group_everyone`) app. The local harness enables both automatically.
- **The recordings setup now reports its own health.** Setting up the recordings folder used to fail into a log line, leaving an app that looked healthy while showing nobody their recordings. `GET /operator/status` now reports whether the Team folder, its permissions and the universal `everyone` mount are actually in place, names the step that failed and the likely cause, and returns 503 when the app cannot serve recordings — so a missing Group folders or Everyone Group app is visible instead of silent.
- The production deploy is now a committed, parameterised script
  (`ops/deploy/deploy-exapp.sh`) driven by an inventory file, instead of a
  one-off on a maintainer's laptop. It is dry-run by default, reads the live
  rollback target before touching anything, and refuses to deploy a moving tag
  (`latest`, `latest-cuda`, …) or an image whose child manifests are missing
  from the registry. CPU and GPU deployments differ by one inventory value, the
  daemon's compute device — there is no separate GPU path.
- `docs/exapp-update-constraints.md` states what the Nextcloud admin UI's
  Install and Update buttons can and cannot deliver — most importantly that
  deploy environment is applied at container creation only, so a release adding
  a *required* environment variable is a breaking change the Update button
  cannot deliver.
- **A retention policy for per-run working files**, `--artifact-retention` / `CASSINI_ARTIFACT_RETENTION`. Disk use grew with every recording and every rerun and nothing ever reclaimed it. The default (`sealed`) removes a completed run's working copies — all of which are duplicated in the operator's canonical library or were temporary staging — and keeps its sealed meeting file and every log. `superseded` only removes runs that a rerun has replaced; `all` keeps everything, as before — except a delivered run's staging copy, which is always removed once the recording reaches its destination so that no full copy of it is left outside the access model. Nothing removes the last copy of anything, and published recordings are never touched.
- **Installing Cassini now tells you whether recordings will actually work.** Setting up the recordings folder used to fail into a log line, so an app whose setup had not completed still enabled, answered every request, and showed nobody their recordings. `GET /operator/status` now reports that setup under `recordings_access` as **provisioned**, **unavailable** (a named thing is missing — it says which app to install, or which setting to fill in), **degraded** (a setup call failed), or **unknown** (the app was restarted without being re-enabled), and returns 503 for anything that is not working. The two Nextcloud apps Cassini cannot install for itself — Team folders and Everyone Group — are now checked by name before setup starts, and reported individually.
- `GET /operator/setup` — a USER-level route reporting whether recordings can be served (`ok` and `state`) and nothing else. It is what lets a non-admin be told that an install was never finished; the diagnosis (which step, which administrator, which paths) stays on the admin-only `/operator/status`. It answers 200 in every state, including the broken ones, so a browser can tell "Cassini is not set up" apart from "the app is down" — `/operator/status` remains the endpoint that answers 503 for monitoring. Existing installs pick the route up when the app is next registered or updated.
- **A one-shot migration for recordings published by an older version.** Recordings made before Cassini stored them in Nextcloud Files live only on the app's own storage, and nothing publishes them again. `./scripts/backfill-nc-files.sh` moves them across, run once by hand after updating; `--dry-run` reports what it would move without changing anything. Migrated recordings are readable only by the Cassini service account, because the audience a recording had when it was published cannot be recovered afterwards — grant access from the Files app, or use `--public` to make them readable by every signed-in account as they were before Cassini had access control. The migration changes nothing when Nextcloud Files already holds recordings, or when there is no older archive to move, so it is safe to run when you are unsure whether it is needed — and skipping it entirely is a supported choice: the old recordings simply stay where they are and everything published from now on works normally.
- **Read your meetings from outside Nextcloud: `cassini meetings`.** An agent or script on a laptop or container can now list the recordings a Nextcloud account is allowed to read (`cassini meetings list`), download one as its single portable `.opus` (`cassini meetings fetch <id>`), or print one as readable context — transcript plus generated summary, as markdown or JSON (`cassini meetings context <id>`). It authenticates as a Nextcloud user with a Nextcloud **app password**, so no interactive browser login is needed and no new server route was added: the commands drive the app's existing per-recording read surface, which fetches from Nextcloud Files as the calling user. Nextcloud therefore enforces exactly the same permissions the in-Nextcloud viewer obeys — a recording you may not read is reported as not found, never as forbidden, so it never reveals that it exists. The surface is read-only; starting, stopping and deleting recordings remain administrator actions. `context` labels its transcript `derived-from-words`: a published meeting carries word-level timings, so paragraph breaks are inferred from pauses and speaker changes rather than editorially cleaned up. Requires `ffprobe` for `context`. Downloaded recordings are written readable by their owner only, since they hold a private meeting's audio and transcript. The CLI refuses to send your credentials anywhere other than the Nextcloud you named — it does not follow redirects, and it rejects a catalog entry pointing at another host. See `docs/agent-meeting-access.md`.
- **Working-file retention is now configurable on an installed app.** `CASSINI_ARTIFACT_RETENTION` is declared as a deploy option, so administrators can choose to keep every per-run working file (`all`) when diagnosing a problem. The default is unchanged.
- `cassini meetings` warns when `--insecure` is used with an app password, since disabling certificate verification exposes that password to anything able to intercept the connection.
- Added explicit LAN media, signaling, and Talk callback configuration for running the full installed-ExApp harness on Docker Desktop for Mac, with fail-fast validation and a setup runbook.

### Changed
- Image publishing now verifies that every keep-forever tag — `:latest`, `:latest-cuda`, `:latest-rocm`, `:cuda`, and each `:X.Y.Z[-cuda|-rocm]` release pin — is actually pullable, failing the run instead of leaving a tag that resolves but points at a deleted manifest.
- The `operator/status` `talk` block now reports `secret_source` (`env` | `generated` | `unset`) and the derived `recording_backend_url` (never the secret value), so admins can see at a glance how the recording secret was provisioned and what to register in Talk.
- The operator now selects where published meetings are delivered with `--sink` / `CASSINI_PUBLISH_SINK`. The only sink today is `local` — the operator's own site root, which is what publishing has always done — and it is the default, so existing deployments need no change. An unrecognised name is rejected at startup with the valid names listed, rather than quietly publishing somewhere unintended.
- The faithful installed-ExApp CI gate refuses its negative-test env hooks
  (`D453_EXPECT_CONFIG_FAILURE`, `D453_FAIL_AT`) unless `D453_ALLOW_TEST_HOOKS=1`
  is also set, so a stray hook variable in a CI job fails loudly instead of
  quietly weakening the gate.
- The demo sandbox now runs on **Nextcloud All-in-One (AIO)** instead of a hand-rolled docker-compose stack that reused the CI/dev harness. AIO provides Nextcloud, Postgres, the Talk HPB, and the reverse proxy — mirroring a real deployment. The sandbox no longer references anything under `harness/`. Cassini is installed/updated on top of AIO with a single idempotent `sandbox/wire-cassini.sh` (App Store release by default); one-time AIO + reverse-proxy + firewall setup is documented in `sandbox/README.md`.
- Cassini's in-Nextcloud control-panel and viewer now render entirely through AppAPI's native embedded-UI mechanism, under Nextcloud's normal Content-Security-Policy. A stock Nextcloud + AppAPI install shows the admin control-panel and viewer with no modifications to AppAPI and no `app_api` integrity warning — the development-only CSP patch that edited AppAPI's signed proxy controller is gone.
- Publishing a recording is now lightweight: `cassini publish` updates the meeting catalog and recordings only and no longer rebuilds or embeds the viewer on every publish. The viewer is served from the app image, so publishing is faster and no longer depends on the viewer build. Pass `--rebuild-viewer` (or set `CASSINI_PUBLISH_REBUILD_VIEWER=1`) to produce a self-contained static site with the viewer embedded, as before.
- Upgrading needs no data migration and no manual step: recordings are stored in a group folder, which is shared storage rather than a personal one, so existing recordings stay where they are and remain accessible to the same people. Cassini installs the dedicated owner group's write mapping and then removes the legacy administrator-group mount and ACL-manager delegation after the service account has successfully managed the migrated root.
- **A recording that does not reach Nextcloud Files no longer counts as published.** Delivery used to run after the publish was already marked successful, and its failures were only logged — so a job could report success with the recording nowhere in Nextcloud and the viewer showing nothing. Delivery is now part of publishing: if the upload, the catalog update or the per-meeting access grant fails, the publish fails, says which step failed, and a rerun re-attempts it.
- An installed app now stores recordings in Nextcloud Files by default. `CASSINI_PUBLISH_SINK` selects the destination explicitly (`nextcloud-files` or `local`), and an installed app whose value is missing defaults to Nextcloud Files rather than quietly keeping recordings on the app's own volume. Selecting `nextcloud-files` without a usable Nextcloud connection now stops the app at startup with an actionable message instead of failing later, one recording at a time.
- **An installed app no longer keeps its own copy of published recordings.** Recordings are stored in Nextcloud Files, but the app also retained a full copy of every meeting it had ever published on its own volume, outside the permissions that govern the originals. That copy is no longer produced: the working directory a publish builds is removed once Nextcloud has accepted the recording, and the app serves meetings only from Nextcloud. A recording the app cannot fetch is reported as missing rather than quietly answered from local disk.
- Talk still receives recording status (started, stopped, failed) exactly as before, so the Record button, the room's recording indicator and failure reporting are unchanged. `CASSINI_TALK_BACKEND_URL` now covers status callbacks and OCS calls only.
- Recording access now uses Nextcloud's virtual `everyone` group, giving new accounts the recordings Team-folder mount immediately without periodic membership reconciliation. Installers must enable both the Team folders (`groupfolders`) and Everyone Group (`group_everyone`) apps — they are the only two manual prerequisites; existing `recording-viewers` ACLs are migrated without changing whether a recording is private or public.
- Whether a conversation is public is recorded at the time of the recording and stays with it. Making a conversation public later does not retrospectively widen recordings made while it was private, and making it private does not withdraw recordings people were already told they could see. If Cassini cannot determine the conversation's type, the recording stays restricted to its participants.
- The recording-permissions runbook now states the access rule accurately: a recording is visible to everyone who had access to the conversation, **including people invited who never joined**, not only those present during the call.
- **Recordings are now access-controlled for everyone, with no way to turn it off.** Per-participant access used to be an opt-in deploy option that defaulted to off, so a stock install shipped an archive where any logged-in Nextcloud user could browse and play every recording. That is gone: an installed Cassini app serves each person only the recordings Nextcloud says they may read, and there is no public-archive mode to fall back to. Nothing to configure — the app sets up the recordings folder and its permissions itself when you enable it. The two things an administrator still does are enable Nextcloud's Group folders ("Team folders") app and the Everyone Group app, neither of which an external app can install on its own.
- The admin deploy option `CASSINI_NC_ACCESS_CONTROL` and the local harness's `--nc-access-control` switch were removed along with it. If you set either, drop it; nothing replaces it.
- The AppAPI register logic is now one implementation
  (`ops/deploy/lib/exapp-register.sh`) shared by the sandbox, the harness
  install phase and the production deploy, so the rules that protect the
  recording archive hold everywhere: unregister before re-register, never pass
  `--rm-data`, and force `PUT /enabled` so the navigation entries come back.
- The ExApp install guide now documents the `/exapps/*` reverse-proxy route to
  HaRP. It is required for every HaRP daemon and is what actually blocks an
  install when missing — the symptom is an app that reports `[enabled]` with no
  navigation icon, which points nowhere near the reverse proxy. It must use
  Caddy's `handle`, not `handle_path`, so the prefix survives.
- The operator's job pipeline has a fourth stage, **seal**, between build and publish, with its own timestamps, log and progress step in the control panel. Publishing is now reached only through a completed seal.
- **A recording is no longer published when the recordings folder is not set up.** Without it, recordings were written into a private folder belonging to Cassini's own service account: the upload succeeded, the job reported success, and nobody could ever open the result. Publishing now fails with the reason and points at `GET /operator/status`; a rerun works once the cause is fixed. This also applies after a container restart until the app is re-enabled, because setup runs when the app is enabled and nothing has verified where recordings would land until it does. To keep recordings on the app's own volume deliberately, set `CASSINI_PUBLISH_SINK=local`.
- The install guide now lists both required Nextcloud apps under Prerequisites, documents every deploy option, and explains how to read the setup report.
- **An unfinished install now explains itself in Cassini, instead of failing with `HTTP 502`.** When the recordings folder is not set up, opening Cassini no longer shows a failed meeting list — it shows what is wrong, and it says something different depending on who is looking. An **administrator** gets the step that stopped: the missing Nextcloud app named by name and id with the `occ app:install` line for it, or `CASSINI_NC_ADMIN_USER` when no administrator could be resolved, or the container log to read when a setup call simply failed and there is nothing to install — plus the disable/enable pair that re-runs setup, and the same sentence the container log carries. **Everyone else** is told that Cassini is not set up, that it is not their account, and is given a link to this Cassini page to send to an administrator — who, opening it, sees the instructions. Which message you get is decided by the same boundary that decides whether you see the Operator tab at all.
- Where the message goes depends on whether recordings can still be **read**, which is not the same question as whether setup finished. When nothing is mounted, it replaces the meeting list, because the list would otherwise be an error or an empty lie. After a plain container restart — where setup has not re-run, so publishing is refused, but every recording already published still opens — it is a strip above the list and the list stays.
- **Enabling or updating the app no longer re-uploads your whole recording archive.** It used to copy every recording it had ever published into Nextcloud Files again on each enable, install and update, under a fixed time budget for the entire batch. Past a certain archive size that ran out of time before it could update the recording list — and because the list is written last, it stayed frozen at its previous contents permanently, with new recordings delivered but invisible and nothing said about it. Recordings have gone straight into Nextcloud Files as part of publishing for some time now, so nothing depended on this any more.
- All three Go modules now declare the same minimum Go version (1.24), matching the toolchain the release images have always built them with. Previously two modules declared 1.22 and one declared 1.24, so the version a module was checked and formatted under depended on which module it was.

### Removed
- `sandbox/compose.sandbox.yml`, `sandbox/deploy.sh`, and `sandbox/destroy.sh` — the harness-coupled compose sandbox they implemented is superseded by the AIO-based sandbox.
- **Cassini no longer uploads recordings to Nextcloud Talk.** Every Talk-button recording used to file a raw `.mkv` into the room owner's `/Talk/Recording/<token>/` through Talk's recording-store endpoint, in addition to publishing the meeting as a portable `.opus`. That second copy sat outside Cassini's canonical recordings root and outside its per-file access controls, so a meeting could be readable there by people it was never shared with. The upload is gone — including the rerun path that re-attempted it — and a meeting now reaches Nextcloud exactly once, as the published `.opus`.

### Fixed
- CUDA image tags (`:X.Y.Z-cuda`, `:latest-cuda`, `:cuda`) can be pulled again. Image pruning had deleted the manifests those tags pointed at, so `docker pull` failed and a CUDA deploy daemon silently fell back to the CPU image — running transcription without GPU acceleration and reporting no error. Tags published before this fix stay unpullable until republished; `:latest-cuda` and `:cuda` repair themselves on the next push to `main`.
- `cassini dev stack up --resume` now recreates containers and mounts the existing Compose and ExApp data volumes after a normal `stack down`, instead of requiring the removed containers to still exist.
- **Publishing a recording no longer re-exports the whole library.** Every publish used to rebuild and rewrite every meeting in the archive, so the time it took grew with the archive — on a production instance with 67 meetings that was roughly seven and a half minutes per recording, during which the job sits at `publish / running` and looks stuck. A publish now exports only the meeting being published and merges it into the live site, leaving every other recording's files untouched. Re-publishing a meeting (for example via a rerun) updates its entry in place rather than adding a second one.
- The three-songs harness sync check now fails loudly when the recorder report
  is missing or contains fewer than 2 composed sessions, instead of silently
  skipping; the recorder run now writes the report the check needs.
- The recorder now rejects `--request-offer-interval 0` at startup instead of
  silently disabling every capture-recovery path, which could leave an empty
  recording for the whole call after a single dropped requestoffer.
- Setup no longer assumes the administrator is called `admin`. Cassini probes for one — the configured account, then `admin`, then the instance's own account list — so instances that name theirs differently can complete setup. If none of them is an administrator it says so and stops, rather than continuing as an account that may not exist; `CASSINI_NC_ADMIN_USER` names one directly.
- Publishing a recording no longer rewrites the whole Nextcloud Files archive. Each publish uploads its own recording and adds it to the shared catalog, so a delivery that fails can no longer remove other meetings from the list.
- A recording you are not allowed to see now reads as "not found" rather than "forbidden". Reporting a denial told you the recording existed, which is exactly what the access model is meant to prevent. Genuine outages are still reported as errors, and denials are still distinguishable in the operator's logs.
- The internal site manifest (`cassini.json`), which lists meeting counts and job ids, is no longer readable by any signed-in user of an installed app.
- The viewer no longer treats an unreachable meeting list as an empty one. A Nextcloud outage now surfaces as an error instead of an empty archive.
- **Recordings of public conversations are now readable by everyone, as you would expect.** A conversation anyone with the link can join was treated exactly like a private one, so its recording was restricted to whoever happened to be on the attendee list. That was worst for the most public meetings: participants who joined by link rather than by invitation cannot be granted access individually, so a public meeting full of link guests produced a recording only its owner could open. Recordings of public conversations are now visible to any account on the Nextcloud.
- **A newly created user can now see public recordings straight away.** The recordings Team folder now uses Nextcloud's virtual `everyone` group, so every account has its mount from creation instead of waiting for a periodic membership sweep. A new account sees everything it is entitled to on its first Cassini visit.
- **A public recording no longer loses its broad access when the app restarts.** A periodic integrity sweep re-applies the restrictive permissions to any recording that is missing them, and it mistook a public recording's deliberately broad grant for a missing restriction — quietly turning every public recording back into a participant-only one. The sweep now leaves a recording's own permissions alone, whichever way they were set, and only repairs recordings that carry none at all.
- **A momentary Nextcloud Talk hiccup no longer costs a recording.** Working out who a meeting belongs to happens once, at publish time, and now gates publishing — so a single failed request used to fail the recording outright, recoverable only by re-running the job by hand. The lookup now retries, and then falls back to asking as the recordings owner, which is the case retrying alone cannot fix: the person who started the recording may have left the conversation, been removed or been disabled between the meeting and its publication. A meeting whose participants are all guests or federated users still publishes successfully and stays visible to its owner only.
- **The recordings list no longer gets stuck on "Meeting not found".** Opening the viewer before its first recording exists — or during any brief Nextcloud hiccup — could leave the right-hand pane showing an error that stayed there even after the list loaded, until you clicked a meeting or reloaded. A link to a specific meeting opened in that window was also dropped instead of opening once the list arrived.
- `bin/cassini` no longer leaks a ~17 MB temp directory on every invocation (about 3.7 GB/day on a dev VM running the harness). The wrapper now builds the CLI to a stable path under `${XDG_CACHE_HOME:-$HOME/.cache}/cassini/bin` and reuses it, so there is nothing to clean up; concurrent invocations stay safe via an atomic rename, on macOS too.
- **A recording is no longer published before its downloadable meeting file exists.** The portable `.opus` — the single-file meeting you download, share and archive — used to be produced in the background *after* the recording had already been handed off for publishing. If that step failed, was interrupted by a restart, or was overtaken by a second run of the same recording, the recording could still be reported as finished while its meeting file was missing, stale, or belonged to a different run. Packing that file is now a stage the recording has to pass: it is written once, checked, and fingerprinted before publishing starts, and the file that reaches the viewer is verified to be that exact file. A failure now fails the recording, with the reason recorded and a rerun available, instead of disappearing into the log.
- **Re-running a recording can no longer overwrite the previous run's meeting file.** Each run now writes its own, so the two cannot race.
- **A failed publish can no longer leave the recordings page without its viewer.** Refreshing the site's viewer files used to delete them before copying the new ones in; an interrupted copy left the page listing recordings it could no longer play. The new files are now staged beside the old ones and swapped in, so a failure leaves the previous, working page exactly as it was.
- **An interrupted replacement can no longer destroy a meeting file.** `cassini pack` removed the previous `.opus` before moving the new one into place; it now replaces it in a single atomic step.
- **Setup no longer assumes the administrator is called `admin`.** Cassini used to look up the administrator with a request made *as* the administrator it had not found yet, so on an instance whose administrator is named anything else the lookup failed, it carried on as `admin` regardless, and every subsequent step was rejected with nothing explaining why. It now asks Nextcloud who the accounts are and finds an administrator among them; if it cannot, it stops and says so, naming `CASSINI_NC_ADMIN_USER` as the way to point it at one.
- **A recording whose permissions could not be applied is no longer reported as published.** Nextcloud accepts a permission change on a file outside a Team folder with a success code that hides a per-property rejection, so the recording could be stored with no restrictions at all while everything looked fine.
- **An administrator whose install was broken no longer loses the Operator surface.** Cassini decides whether to show the operator by asking the admin-only status endpoint, and that endpoint answers 503 when recordings cannot be served — which was being read as "not an administrator". The one person who could fix the install saw the same browse-only app, and the same unexplained error, as everyone else.
- Catalog meeting dates now come from the pack's recorded `createdAtUtc` (rendered in UTC), so meetings whose file name carries no timestamp — e.g. backfilled dailies — show a real date and sort correctly instead of echoing the raw id. Already-published archives pick this up on their next export.
- **`docs/portable-meeting-format.md` no longer tells consumers to reject every file Cassini writes.** The file-identification and required-tag sections still demanded `CASSINI_FORMAT=org.cassini.portable-meeting/1` even though the producer has emitted `/2` since the multi-transcription format landed. Both sections now state that consumers must accept `/1` and `/2`.
- **A recording delivered to Nextcloud Files is now verified to be the file the recording actually produced.** Cassini fingerprints each meeting when it is packed and re-checks that fingerprint before publishing; the check was applied when recordings were stored on the app's own volume, but not on the Nextcloud Files path an installed app uses. A recording whose file does not match what was packed is now refused before anything is uploaded, so a half-delivered recording can no longer appear in the archive.
- The standalone operator container no longer risks clearing more than its own site directory when started with an unusual `CASSINI_OPERATOR_SITE_ROOT`.
- The recordings migration script (`backfill-nc-files.sh`) now runs on macOS's system bash, where invoking it with no options previously aborted.
- The local test harness now stops with a clear message when Nextcloud Talk fails to install, instead of continuing and failing much later with an unexplained error.
- Fixed harness startup under the macOS system Bash when optional Compose or Nextcloud command arguments are empty.

Every logged-in user gets the meeting-browsing app; the operator/recording-control surface returns as an admin-gated surface *inside* the one app in a follow-up (D-420 V3), and the operator JSON API stays admin-only throughout (unchanged security boundary). No change for viewer users.

### Fixed
- Fixed harness teardown and bring-up edge cases so repeated runs no longer leave stale containers/networks or duplicate `signaling-public-proxy` aliases.
- Cassini shell polish (D-420 review follow-ups): switching between the **Browse** and **Operator** surfaces now keeps the open meeting in the URL (deep-link no longer dropped); the operator surface uses the same light/dark theme as browse (stored preference, then OS) instead of only the OS setting; and the in-Nextcloud mount targets the innermost `#content` more robustly.
- Added the missing `operator/settings` proxy route so the operator surface's STT-quality Settings panel works through the Nextcloud AppAPI proxy (it previously had no route and would have 403'd/404'd), and dropped the now-dead `control-panel` proxy routes left over from the collapsed second entry.
- Talk recorder: stabilized subscriber negotiation behind intermittent empty/blank recordings ("no remuxable streams found in session artifact", silent MKVs, and 0-word transcripts). A fresh in-call participant previously caused two empty-SID `requestoffer` messages; the second could make the MCU tear down and recreate its Janus subscriber, rotating the SID while the first offer was still being answered. Initial and exhausted-peer recovery now issue exactly one request, repeated in-call snapshots keep the valid response throttle, and inbound offers cannot trigger recovery in front of themselves. The recorder also sends its answer without waiting for full ICE gathering, queues trickled candidates behind the matching answer, and emits end-of-candidates only after gathering completes (D-454).
- Stopping a recording no longer fails with "job is not stoppable" when the operator has just reported the job as running. The stop registration now brackets the whole time the job is advertised as recording, so a stop is accepted from the moment the job goes running until it leaves the record stage, and one arriving before the recorder has finished starting up is delivered as soon as it does.
- A stop requested after the recording has already ended on its own (while the operator is still uploading to Talk and queueing the build) is now accepted and recorded as a stop request instead of being rejected; the job's stop reason continues to report why the recording actually ended.
- The release pipeline's required "Faithful installed ExApp" gate now decides whether to run from a deny-list (run unless a change is purely docs/notes/assets) instead of an allow-list of enumerated product paths, so a pull request touching a build input nobody thought to enumerate can no longer report the required check green without actually building and recording.
- Talk recorder: closed two gaps that could still lose media on a call the recorder appeared to be recording normally. A participant whose handshake completed but whose media never arrived was left untouched for up to ~45 seconds, so short calls (a ~30s 1:1) could still finalize as empty ("no remuxable streams"); such a peer is now rebuilt about 12 seconds after its answer, but only while its connection is not actually established, so a slow-but-healthy participant is never torn down. A participant who turned their camera on mid-call could also be wedged permanently by a dropped signaling answer — their audio kept recording while the newly added video was silently lost for the rest of the call; the recorder now retransmits that answer as the signaling connection recovers, within a bounded budget, instead of skipping the participant forever (D-509).
- Fixed the CI session-artifact guard passing recordings that captured no media. It verified headers and index framing but never counted packets, so a capture with a valid header and a 0-byte index reported "session artifact verification passed" — the exact empty-capture class (D-454) the per-PR e2e leg is relied on to catch. The guard now walks each stream log and requires real RTP media packets per captured stream, counted kind-aware so a stream carrying only RTCP no longer passes for having non-empty bookkeeping.
- Fixed the A/V drift check reporting success without measuring anything. It exited 0 when no audio/video pair was found, and also when pairs were found but every one was too short to compare — printing "av drift check passed" after zero comparisons. Drift runs now require at least one pair to be actually compared, and the rejoin leg, which legitimately records video-less, opts down explicitly.
- Fixed the e2e leg never producing a drift pair the check could measure. The publisher bots play the sample fixture once and stop at its end, and the default fixture is 15s — capping the measurable pair at ~11s against the 15s minimum regardless of the configured publish window. The leg now prepares a fixture sized to the publish window. The fixture is also rendered with a keyframe at least every 0.5s (libvpx's default 128-frame interval delayed decodable video up to ~4.3s behind audio, which the elapsed-difference metric misread as drift), and the leg's tolerance carries a documented budget for the remaining structural skew.
- Fixed panels, cards and form fields losing their borders and shadows inside Nextcloud, which left content areas with nothing to separate them.
- Fixed high-contrast themes leaving those same areas undefined, and the selected recording unmarked.
- Fixed Nextcloud's app chrome applying twice, which added a second header-height gap, doubled the side margins, and clipped the bottom of the app.
- Fixed the shell tab bar, the operator scrollbar gutter, and the detected-hardware values rendering with the wrong colours under some themes.
- Fixed the recordings list not appearing on narrow screens.
- Fixed the settings Save button offering to save when nothing had changed.
- Fixed the meeting filter drawing a second focus ring inside its own.
- Fixed the meeting load-in fade stalling and then snapping into place.
