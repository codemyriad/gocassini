Recommended direction

A stable retrieval contract; a thin, local SQLite read model is the leading persistent backend.

Ship this in two independently useful steps. First, expose cassini.meetings.context.v1 from bounded file prefixes instead of whole audio—no database required. The low-level index returns references; the first useful agent workflow hydrates bounded excerpts as the caller before loading selected full meetings.

The actual answer to “do we need a DB?”

Not for known-meeting or “process all selected meetings” workflows. Probably for repeated ad-hoc search across a growing archive. The team endorsed the capability but previously asked that FTS/RAG complexity earn its place in evals. Once adopted, the DB is persistent—not ephemeral—and rebuild is a migration/recovery operation.

Frame

The job is retrieval, not a new content platform.

An LLM needs two distinct operations: find likely moments across the meetings it may read, then load selected meeting context. Search data is a deterministic projection. A saved summary or synthesis is a different, authored artifact with provenance and a still-open multi-meeting audience model.

Files are durable truth

The published catalog and self-contained Opus meeting survive moves, backups, and complete index loss. SQLite persists in normal operation but can be reconstructed exactly.

Nextcloud is access truth

No permissions or group membership are copied into the search DB. Revocation changes the next request immediately.

Context is a wire contract

CLI, app preparation, agent skills, and later adapters consume the same versioned context.v1 representation.

“Contentless” does not mean secret.

FTS5 can omit a retrievable transcript column and make a references-only response structural, but someone with the database file can still reconstruct much of its vocabulary and ordering. Keep it owner-only, disclose it as transcript-derived storage, and treat the operator volume as sensitive.

Do not conflate two “Nextcloud DB” options

Reading Nextcloud’s internal tables for files or ACLs is the direction discussed on 30 Jul and should remain rejected. Those tables are not Cassini’s API, and direct SQL does not safely reproduce Files authorization.

Cassini-owned app tables are legitimate for a native PHP app through Nextcloud’s supported database API and migrations. They would share the administrator’s existing backup, replication, HA, and monitoring regime. That option was not resolved by the meeting discussion and deserves to remain on the table.

Why operator-local SQLite still leads

Cassini is currently a Go AppAPI ExApp, not a native PHP app. AppAPI gives it HTTP APIs and a persistent volume, but its documented APIs do not expose arbitrary app tables. Current AppAPI only extracts ExApp metadata and translations; it does not install executable PHP or run migrations from the ExApp package. A supported Nextcloud-table design therefore needs a separately installed native companion app with its own app ID and a private API to Go—or an AppAPI enhancement. Directly injecting Nextcloud DB credentials into the ExApp would instead create deployment and coupling problems.

The operator already runs migrated jobs.sqlite3 on that persistent volume, so a native companion would not eliminate ExApp persistence. A separate search.sqlite3 adds no database service, credentials, or engine matrix, and can be rebuilt/swapped without touching job history. It also gives every supported Nextcloud deployment the same FTS5 behavior; Nextcloud itself may use MariaDB, PostgreSQL, or SQLite, whose full-text features are not portable.

When Nextcloud-owned tables would become the better shape.

Revisit Shape C if Cassini must run multiple operator replicas against one index, if administrators require the index in central database backup/restore, or if a native Nextcloud search provider becomes a product requirement. Do it as a separately installed native companion with Cassini-owned tables and Files-API authorization—not by sharing Nextcloud’s raw database credentials. Until one of those conditions exists, the second app lifecycle, extra PHP/API boundary, primary-database load, and cross-engine search work buy little user value.

What the no-DB slice still buys us.

Bounded prefix reads make one or a handful of known meetings cheap. They also serve workflows that intentionally process every selected meeting, where retrieval adds no value and can hide relevant context. A simple scan/filter implementation behind the stable search contract provides a baseline. FTS earns activation by materially improving recurring ad-hoc questions at acceptable operational cost.

Read path: search refs → caller-authorized excerpts → selected full contexts. Write path: successful publish → best-effort index ingest. Recovery path: build, validate, and swap a replacement projection.

Resolved implementation seam: reuse the process boundary first.

A compiled cassini inspect --transcript recovered and validated timed-word metadata from capped prefixes in about 40–50 ms locally; all nine fixtures succeeded by 512 KiB. Because ffprobe needs a few early audio pages after the OpusTags packet, this is a bounded prefix—not a tags-only read—but it cannot scan or decode audio beyond the staged cap. A new machine mode still has to invoke the existing context.v1 builder. The operator already validates and ships CASSINI_BIN plus ffprobe. A shared Go module would stop exactly after OpusTags and remove temp files, roughly 56 MiB of short-lived subprocess RSS per decode, and a native parser boundary, but is estimated to add 3–5 days before user value. Promote if p95 local decode exceeds 250 ms, extraction queues exceed 2 seconds, failures exceed 1%, memory limits constrain useful concurrency, or another streaming Go consumer appears.

1 · Hydration path

  • Resolve meeting ID from the caller-filtered catalog; never infer a filename from the ID.
  • Validate exactly one local asset shaped like meetings/<name>.opus; reject traversal, duplicate basename, or malformed mappings.
  • Read prefix ranges progressively—proposed 512 KiB, then 1/2/4 MiB, with a validated configurable cap and an 8 MiB hard ceiling.
  • Force Accept-Encoding: identity, validate Content-Range, and refetch from byte zero pinned to one ETag with If-Match. Abort or restart if the source changes.
  • Refuse redirects so AppAPI credentials cannot follow them. If upstream ignores Range, read only cap + 1 and close directly. Never fall back to downloading audio server-side.
  • For the MVP, stage the capped prefix in a private temp directory and call the already-shipped cassini inspect decoder. Retry only a typed need_more_metadata; checksum, JSON, limit, and malformed errors are terminal.
  • Decode portable v1/v2 and emit canonical cassini.meetings.context.v1.

2 · Search path

  • Resolve the AppAPI user; missing identity is an infrastructure error.
  • PROPFIND the caller’s visible recording basenames and load a strict catalog snapshot.
  • Use the same response contract for the capped scan baseline and an indexed backend.
  • For FTS, join that allow-set in SQL before MATCH, ranking, and LIMIT.
  • Return meeting metadata plus timestamp/speaker references—no text, score, or archive-wide counts.
  • Use a bounded first page only in v1; do not pretend offset pagination is stable across index or permission changes.
  • For the user-facing workflow, group top refs by meeting and re-read each prefix as the same caller to emit short excerpts with surrounding context.
  • Hydrate chosen full meetings in one separate bounded, streaming batch.

Excerpts are a transcript-disclosure surface even though search itself is references-only. Each unique source is re-read through Nextcloud as the caller; a denied meeting or changed revision emits a typed unavailable/retry line rather than text from the index. For both excerpt and context batches, the lean is ordered per-line errors with a request-level failure only when authorization infrastructure is unavailable.

Minimal search projection

PRAGMA journal_mode = WAL; PRAGMA user_version = 1; CREATE TABLE indexed_meeting ( opus_name TEXT PRIMARY KEY, source_etag TEXT, source_digest TEXT, context_version TEXT NOT NULL, window_count INTEGER NOT NULL, indexed_at TEXT NOT NULL, state TEXT NOT NULL, error_code TEXT ); CREATE TABLE window_ref ( rowid INTEGER PRIMARY KEY, opus_name TEXT NOT NULL REFERENCES indexed_meeting(opus_name) ON DELETE CASCADE, ordinal INTEGER NOT NULL, start_ms INTEGER NOT NULL, end_ms INTEGER NOT NULL, speaker_id TEXT NOT NULL, UNIQUE(opus_name, ordinal, speaker_id) ); CREATE VIRTUAL TABLE window_fts USING fts5( text, content='', contentless_delete=1, tokenize='unicode61' ); -- The security-critical ordering SELECT r.opus_name, r.start_ms, r.end_ms, r.speaker_id FROM window_fts f JOIN window_ref r ON r.rowid = f.rowid JOIN json_each(?1) visible ON visible.value = r.opus_name WHERE window_fts MATCH ?2 ORDER BY rank LIMIT ?3;

Window proposal: deterministic 30-second wall-clock windows every 15 seconds, with one row per speaker represented in the window. Do not index display names or speaker labels. Tune only after evaluating real queries.

Persistent in normal operation; rebuildable by design.

search.sqlite3 is expected to remain in place indefinitely, survive restarts, and receive incremental publish/reconcile updates. “Rebuildable” is the recovery and migration property: create search.sqlite3.next beside the live DB, complete and validate a coherent archive pass, then atomically swap it in. Only the superseded copy is removed after rollback confidence. Because its contents are transcript-derived and reproducible, deployments may exclude it from backups—but any retained copies must receive the same sensitive-data controls.

01

Ranked or chronological?

FTS5’s global BM25 statistics can weakly influence ordering even after the live visibility join. Raw scores and counts stay hidden, but ordering remains a corpus oracle.

Lean: ranked results + rate limits; decide explicitly.
02

References or snippets?

References keep transcript bytes behind Nextcloud but cost a batch round trip. Snippets improve relevance judgment but make the search handler a text-disclosure surface.

Lean: refs-only search API; first CLI/app workflow immediately hydrates bounded excerpts as caller.
03

Process bridge or shared module?

The recorder owns the only Go decoder/context builder; the operator already ships and invokes the cassini binary. A process bridge is the smallest coherent change. A shared pure-Go module removes process overhead but creates module and container-build work.

Lean: process bridge for MVP; promote after measured batch overhead.
04

How fresh must search be?

Publish-time ingest is fast but can fail independently. Rebuild and reconcile cadence determines how quickly repaired, replaced, or deleted sources converge.

Lean: non-fatal ingest + explicit rebuild + daily reconcile.
05

Partial or ready-only search?

Immediate partial search is useful during a large backfill but easy for agents to mistake for the complete corpus. A negative result is invalid whenever searchable < visible. Returning 503 until one coherent pass is simpler but delays first use.

Lean: partial is explicit; CLI refuses to phrase it as “no match.”
06

Duplicate overlapping hits?

Thirty-second windows on a fifteen-second stride improve boundary recall, but adjacent rows can represent the same passage and consume the result limit.

Lean: collapse adjacent hits per meeting before the final limit.
07

What happens with a local sink?

Without nextcloud-files, there is no per-caller Files authorization substrate. Treating local development as implicitly public can hide a production security bug.

Lean: disable user routes; require an explicit dev-only policy.
08

How much concurrency?

Every search performs a visibility scan; every hydration may start an external decoder in the MVP. Each measured process briefly used about 56 MiB RSS. Unbounded batches can exhaust DAV, memory, or process capacity.

Lean: per-caller rate limit + process-wide semaphore 2; backfill gets 1 slot.
09

Which backend earns activation?

The stable contract can be backed by known-meeting lookup, an authorized linear scan, local FTS, or later semantic retrieval. Building the contract does not decide the engine.

Lean: measure scan first; enable FTS only when recurring real questions materially improve.
10

Where should the index live?

Nextcloud-owned tables inherit central database operations but require a native companion and portable full-text behavior. Local SQLite reuses Cassini’s existing ExApp persistence and one implementation.

Lean: separate local search.sqlite3; revisit for multi-replica HA or native-search integration.
Implementation plan

Deliver vertical slices without making the database authoritative.

The first slice removes today’s largest inefficiency and ships independently. The search API is then evaluated with a simple baseline before persistent FTS becomes the enabled backend.

Slice 0

Expose the existing decoder as a bounded machine seam

Extend cassini inspect with a versioned context-JSON machine mode and catalog ID. Probe compatibility once at operator startup because CASSINI_BIN is configurable. The operator stages only a capped prefix, invokes the decoder under a timeout/semaphore, kills the whole process group on cancellation, caps stdout/stderr, and deletes the private temp directory. Do not duplicate the portable decoder.

  • Golden equivalence across portable v1/v2
  • Limit tag/chunk counts, base64/gzip expansion, decoded JSON, and word/item counts before accepting untrusted metadata; declared sizes are not trusted limits
  • Return typed “need more” separately from malformed, corrupt, or oversized
  • Use an explicit ephemeral /tmp root, 0700 directories, 0600 files, and startup scavenging—do not inherit the image’s persistent TMPDIR
  • Define a canonical cross-version transcript digest; never call the v1 manifest hash a transcript hash
  • Malformed, duplicate, traversal, oversized-tag fixtures
  • Record process overhead; promote to a shared pure-Go module only if needed
1–2 daysHigh-leverage seam; estimate needs owner validation.
Slice 1

Fast single and explicit batch context

Add user routes in the operator, progressive caller-authenticated Range reads, canonical JSON, streaming NDJSON batch, and CLI capability detection with the existing local full-download path retained only for old servers.

  • Process-wide deadline and semaphore; request body, batch count, stdout, stderr, and decoded-byte caps

Slice 2

Ship the stable search contract with a scan baseline

Add POST /published/search behind a SearchBackend interface, initially scanning a capped caller-visible archive. Add the CLI orchestration that immediately turns returned references into bounded, caller-authorized excerpts, then loads full context only for selected meetings.

  • Small server-built query grammar and bounded first page
  • Explicit maximum scan corpus and partial-coverage semantics
  • No query body, transcript, score, or global count in logs or response
  • Denied/absent hydration is 404; changed source revision is a typed retry

Checkpoint

Decide whether persistent FTS earns activation

Test actual agent tasks against realistic accessible archives. Compare known-meeting, all-selected-meetings, the shipped scan baseline, and an offline FTS prototype. Use evidence to decide whether a persistent index improves enough recurring questions to justify its lifecycle.

  • Define 20–30 expected-result questions; include exact terms, paraphrases, names, dates, and known failure cases
  • Measure top-10 recall, task completion, latency, bytes, visible meeting count, and coverage—not live query text
  • Verify important examples against surrounding transcript and audio because real transcripts have omitted and misordered speech
  • Record the chosen storage placement separately: local SQLite now, or a native Nextcloud companion if its operational benefits justify the extra boundary

Slice 4

Make indexed search permission-correct and operable

Join the live caller-visible basename set inside the FTS query before rank and limit. Reconcile new, replaced, and deleted Opus sources; expose caller-relative coverage; update privacy/operator docs; ship disabled, rebuild, shadow-test, then switch the same API from scan to FTS.

  • Fresh install, volume-loss recovery, migration swap, and stale-source cases tested
  • Per-caller rate limits; privacy language treats the index as transcript-derived storage

Failure modes worth designing first

The dangerous bugs look like convenience.

Filtering after global LIMIT
Hidden meetings can consume the result limit and make visible matches disappear. This is both incorrect and observable. The caller-visible basename set must participate in the SQL query before ranking and limit.
Treating an empty visibility scan as success
The current catalog path sometimes collapses provisioning/upstream failure into an empty catalog. Search cannot do that: “no matches” must be distinguishable from “could not establish what this caller may see.”
Trusting catalog paths via path.Base
A basename is the correct join key, but only after validating a strict local meetings/*.opus asset. Otherwise malformed or external catalog paths can alias the indexed resource. Parse once into a typed snapshot and reject ambiguity.
Silently falling back to whole-file downloads
A Range-ignoring upstream can reintroduce the original 10–30 MB transfer and become a denial-of-service primitive. The server must enforce its own byte cap, close early, and report an unsupported/oversized artifact.
Treating compressed metadata as harmless
OpusTags are caller-selected input to the decoder. Existing unbounded chunk assembly and io.ReadAll over gzip need explicit encoded, compressed, expanded-JSON, word-count, subprocess-output, and time limits before this path becomes a user HTTP route.
Calling contentless FTS “no transcript storage”
It narrows the API and storage shape; it does not make the token index confidential. Backups, volume deletion, access controls, and the privacy page must treat it accordingly.
Letting search state become an insight store
Deterministic timed windows are persistent derived state, but replaceable from source meetings. Saved summaries, decisions, or cross-meeting synthesis require provenance, lifecycle, and a multi-source audience rule. Keep that work in the insight-artifact track.
Treating a transcript hit as an exact quote
Real team use found omitted speech and misordered interjections. Search and context must label text as derived from timed words, carry an opaque source revision and timestamps, and let a user or agent return to the authorized audio before making an important verbatim or attribution claim.

Decision requested

Approve the direction, then settle six gates.

The proposal is deliberately reversible: hydration and the scan-backed search contract stand alone. If FTS is adopted, its live database is expected to remain; schema changes and recovery use a validated build-and-swap rebuild rather than routine deletion. Before indexed search is enabled, the team should record answers to:

  1. Is references-only low-level search acceptable when the first CLI/app workflow immediately hydrates authorized excerpts?
  2. Do we accept ranked ordering’s weak global-corpus signal if scores/counts are hidden and requests are rate-limited?
  3. Is a default 4 MiB metadata cap sufficient, or should it start at 8 MiB?
  4. Should search be available with loudly marked partial coverage, or return 503 until the first coherent rebuild?
  5. Which real-question evaluation and coverage threshold is sufficient to enable persistent FTS for agents?
  6. Does v1 use operator-local SQLite, or do backup/HA/native-search requirements justify a native Nextcloud companion with Cassini-owned tables?
