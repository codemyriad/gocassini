  • C: limiting internal mode to Talk-backend starts was too narrow

Migration for an existing instance

What operators must change

StepRequired changeWhy it matters
1set signaling [clients].internalsecret and restart signalinginternal hello depends on internal-client auth
2set CASSINI_TALK_SIGNALING_INTERNAL_SECRET to the same valuerecorder and signaling must share the same secret
3keep CASSINI_TALK_RECORDING_SECRET correctused for signed recording-auth requests to Nextcloud
4ensure Talk advertises a signaling URL reachable from both Nextcloud and the recordermost likely migration pitfall
5keep/set CASSINI_TALK_BACKEND_URL or connect-url when public and runtime URLs differlets operator/recorder reach the same Nextcloud instance honestly
6expect default behavior to move to hpb-internalgeneric jobs and Talk backend starts no longer rely on guest mode implicitly

Transitional fallback

If rollout needs a temporary escape hatch, use --talk-auth-mode guest-participant or request JSON "talkAuthMode": "guest-participant". There is intentionally no automatic fallback.

Known limits

What D-283 does not try to solve

Explicit non-goals

  • non-HPB or internal-signaling-only Talk support
  • per-backend URL→secret mapping
  • a new recording architecture
  • automatic guest fallback

Residual risk

  • runtime invalidation is now expected to be narrow
  • likely seam: room event timing / payload handling after internal join
  • if local proof fails due to topology, treat that as harness work first

Decision quality

The planning docs were correct to treat D-283 as an auth/bootstrap migration. The risky part left is operational proof, not product-shape redesign.
